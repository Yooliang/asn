# 0.1.113：選項按鈕、回信綁原信、本人許可紀錄

小良哥 2026-10-30 核可（群組 #1695 第 2 點，#1694）：要小良哥回答的信可以附選項按鈕（准／不准、A／B／C），他按了自動回到原信，並寫成「本人許可紀錄」；手機回信自動帶 reply_to，收件端顯示原信第一行。0.1.114 的「審查核可」共用本文的資料結構。

本文件只定設計，不含程式。西川撰寫；動到 security definer 函式的部分由 asn真 最後審。

## 一、要解決什麼

1. **授權要靠翻聊天記錄**：規則是只有小良哥本人算授權，但訊息標頭只寫 `trust=member from=asn真（小良哥）`，AI 每次確認「#425 他說可以了沒」都得逐則翻群組找他自己說的那句。
2. **手機回信沒綁原信**：電腦版回信已帶 `reply_to`（`ui/lib/core.mjs:387`），手機一對一對話沒有（`ui/m.js` 只有群組的 `replySeq`）。結果是 AI 收到的回答不知道在回哪一封，尤其同時問了好幾件事的時候。
3. **收件端看不到被回的是哪一封**：`reply_to` 欄位後台有（`relay.messages.reply_to`），但轉進視窗的信沒有顯示原信內容。

## 二、現況（已查證）

- `relay.messages.reply_to uuid` 已存在；寄信函式 `irori_relay_send` 檢查被引用的信在同租戶，不在就丟掉。
- 電腦版 UI 已帶 `reply_to`（`core.mjs:387`），並用它標記「已回」（`core.mjs:324-358`）。
- 群組用的是 `room_messages` 的 `reply_to_seq`（`rooms.ts:234`），與一對一信件的 uuid 是兩套。
- 信件標頭第三行 `【要回信】回信位址=… 信件編號=…` 由外掛逐字解析（`bridge/mail.rs:198-210`、`MAIL-HEADER.md`），**不能改動這一行**。
- 小良哥本人簽章的信已有 `owner_signed` 欄位（`20261021060000_owner_signed.sql`），可作為「本人按的」的基礎。
- 語音旗標 `voice` 的加法（`20261023110000_voice_flag.sql`：新增欄位＋新的寄信函式，舊函式不動）是現成的前例。

## 三、設計

### 3.1 選項：誰能附、附什麼

- 寄信時多一個選填欄位 `options`：字串陣列，2～4 個，每個 1～20 字、不含控制字元。內部編號用順序（0～3），不收呼叫端給的編號。
- **只有收件人是「人」的信才能附**（收件人是小良哥的人代號／本人帳號）；寄給 AI 的信帶 `options` 回 `bad_request`，不靜默丟掉，免得寄件人以為有按鈕。
- 任何節點都能附（AI 要問小良哥，本來就是 AI 寄的）；**按下去的權限不在寄件人手上**（見 3.2）。
- `asn_send`／`asn-cli send` 加 `options`（`--option 准 --option 不准`，可重複）。信件內文仍要把選項用文字寫出來，因為舊版 ASN 與舊版手機不顯示按鈕。

### 3.2 按下去：本人許可紀錄

新資料表 `relay.owner_decisions`（只有 security definer 函式寫入，沒有任何直接寫入路徑）：

| 欄位 | 說明 |
|---|---|
| `id` | uuid |
| `tenant_id` | 租戶 |
| `message_id` | 被回答的信（一對一）；群組版見 3.6，二選一，檢查約束 |
| `option_idx`、`option_label` | 選了第幾個，**當時的文字快照**（之後原信改不了） |
| `question` | 原信第一行（最多 80 字，寫入時截斷、跳脫），查詢時不用再回頭找原信 |
| `decided_by` | 簽章者的使用者 uuid |
| `decided_at` | 時間 |
| `reply_message_id` | 自動產生的回信 |

唯一鍵 `message_id`：**同一封問題只能答一次**，要改決定就請 AI 重新問一封新的。

按下去呼叫 `asn_relay_owner_decide(p_actor, p_signed_user, p_message_id, p_option_idx)`（security definer，ACL 只有 `postgres`、`service_role`）：

1. 沒有本人簽章，Edge 在打資料庫前就回 401（同 `requestPartnerOp`）；
2. 原信必須是寄給簽章者本人（**只認人代號**，不認其名下節點，與 3.1 一致）、同租戶、帶 `options`、`option_idx` 在範圍內、尚未答過、未過期（預設 7 天，過期回 `expired`，畫面灰掉）；
3. 同一交易內寫入 `owner_decisions`，並產生一封**回信**：`reply_to`＝原信、`owner_signed=true`、寄件人是本人。**回信內文由後台依選項快照組出固定格式**（`【本人許可】<選項文字>`），不收任何自由文字，所以不可能被拿來夾帶指令。

為什麼不讓 AI 自己「查有沒有許可」就算數：按鈕是唯一寫入口，且寫入要本人簽章；AI 的節點金鑰呼叫這支函式一律拒絕（`forbidden`），不能替本人按。

### 3.3 AI 這端怎麼看到

- 回信轉進視窗時，說明行後面多一行固定文字：`（本人許可：<顯示名>按了「准」，針對你 <時間> 的信「<原信第一行>」）`。**顯示名由 `decided_by` 查出，不寫死**；只有簽章者是租戶擁有者時才寫「本人許可」，否則寫成`（<實際按的人的顯示名>按了「准」，針對…）`，不使用「本人許可」字樣。這行由收發室依**後台的結構化欄位**加（比照 `VOICE_NOTE`），內文行首相同開頭的行會被 `escape_body` 跳脫，所以內文冒充無效。
- **許可只對那一封問題有效**：回信帶 `reply_to`，AI 要引用原信編號；許可範圍就是原信問的那件事，不能拿去套別的事。
- 新增唯讀查詢 `asn-cli decisions [--since 時間] [--limit n]`：列出寄給本人、由本節點的人問過的決定（節點金鑰授權，只看自己問過的，不洩漏別人的）。解決「要翻聊天記錄」的問題。

### 3.4 手機回信自動綁原信

- 一對一對話記住「這位夥伴最後一封要回信（`expects_reply=true`）且還沒回的信」；使用者在輸入框送出時，預設 `reply_to` 帶它。
- 輸入框上方顯示一個可關掉的小標籤「回覆：<原信第一行>」，關掉就不帶。沒有符合的信就不顯示、不帶。
- 電腦版已經有，不動；兩邊共用同一個「最後一封待回」的判斷函式，放 `ui/lib/`，守門測試確認兩邊都引用它。

### 3.5 收件端顯示原信第一行

- 收發室轉交一封帶 `reply_to` 的信時，在說明行後面多一行：`（回覆你的信：「<原信第一行，最多 40 字>」）`。
- 原信第一行從本機往來記錄找（`reply_to` 對得上自己寄出的那封，`core.mjs:324` 的 log 已存寄出時的 id）；找不到再問後台（同租戶、且簽章者是該信的收發雙方才給），再找不到就不加這行。
- 這行內容來自對方的信，所以一律經 `escape_body`，並固定前綴；**不動第三行**（外掛解析的那行）。

### 3.6 群組

小良哥的問題大多是在群組裡被問的（#1695 本身就是），所以第一版就要有。群組用 `room_messages` 的 `seq`，所以：

- `options` 加在 `room_messages`（同樣的限制），`owner_decisions` 的參照改成 `(room_id, seq)` 與 `message_id` 二選一（檢查約束保證恰好一個）；
- 按下去走 `asn_relay_owner_decide_room`，驗證簽章者是該群組成員、該則訊息帶選項、尚未答過；產生的回覆用 `room_post_reply` 的現有機制（自動 @ 原作者，`rooms.ts:234`）；
- 群組裡誰都能附選項，選項附在「點名某個人」的訊息上，沒點名人就不顯示按鈕。
- **權限在函式裡驗，不靠畫面**：`asn_relay_owner_decide_room` 要驗①簽章者＝該則訊息點名的那位使用者，不是就拒絕（`forbidden`）；②簽章者是群組成員。
- **「本人許可」只在簽章者＝租戶擁有者時成立**：有外部成員的群組裡，外部成員（也有簽章帳號）被點名並按了，紀錄照留，但 `owner_decisions` 多一欄 `is_owner`（寫入時由函式判定），AI 端那行與 `asn-cli decisions` 都依它區分，外部成員按的一律寫出實際按的人，不寫「本人許可」。

### 3.7 相容

- 舊版 ASN／舊版手機：看到的是一般文字訊息，沒有按鈕；使用者照舊用打字回。信件內文因此要寫明選項。
- 舊版電腦端收到帶 `options` 的信：欄位不認得就忽略，信照轉。
- 後台先部署（新欄位、新函式，舊函式不動），再發新版 ASN，順序同語音旗標。

## 四、安全檢查清單（給審查）

1. 按下去只有一個入口，要本人簽章；節點金鑰一律拒絕。
2. 回信內文由後台依選項快照組出，沒有自由文字。
3. 一封只能答一次；選項文字存快照，原信事後無法改寫已記下的決定。
4. 收件端的「本人許可」行來自結構化欄位，不是內文；內文冒充被跳脫。
5. 不能附選項到寄給 AI 的信（避免偽造「本人許可」的外觀）。
6. `question` 與顯示用的原信第一行都截斷＋跳脫，因為內容來自別人。
7. 群組版：簽章者必須是被點名的人；沒被點名的成員按一律拒絕。
8. 「本人許可」字樣只給租戶擁有者按的；外部成員按的要寫實際是誰，`decisions` 以 `is_owner` 區分。

## 五、分階段（每階段可單獨發版）

1. **手機回信綁原信＋收件端顯示原信第一行**（3.4、3.5）：不動後台，風險最低，先發。
2. **後台**：migration（`options` 欄位、`owner_decisions`、兩支決定函式、寄信函式的選項版）＋ Edge 解析＋測試。
3. **畫面與 AI 這端**：電腦版／手機的按鈕與「已選擇」狀態、轉交時的固定行、`asn-cli decisions`、`asn_send` 的 `options`。
4. 0.1.114 的審查核可沿用 `owner_decisions` 的結構（另有設計文件）。

## 六、測試

- 資料庫（pglite）：非收件人不能按、過期、重複按、選項編號超出範圍、AI 節點金鑰呼叫被拒、群組版非成員被拒、**未被點名的成員按→拒絕、外部成員被點名並按→紀錄留下但 `is_owner=false`、AI 端固定行不含「本人許可」**、約束（二選一）、回信內文固定格式；**還原驗證**：把檢查拿掉測試必須變紅。
- Edge：沒簽章 401；`options` 數量、長度、控制字元的格式檢查；寄給 AI 帶 `options` 回 `bad_request`。
- Rust：轉交時的固定行來自結構化欄位；內文冒充被跳脫；第三行逐字不變（沿用 `MAIL-HEADER.md` 的守門測試）。
- 畫面：smoke 加情境——有選項的信顯示按鈕、按了變成「已選擇」、另一台設備同步；手機回信帶 `reply_to`。
