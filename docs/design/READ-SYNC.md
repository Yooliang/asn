# 已讀多端同步

需求（小良哥）：同一個帳號（本人）在電腦版與手機（可能多台）讀過某個對話，其他端的未讀數與已讀標記也要跟著消掉。

## 做法

- **已讀位置**：每個帳號、每個對話鍵一筆，值是「該對話最後一則收到的信的時間（毫秒）」。用信件自己的時間，不用設備時鐘，所以各設備時鐘不準也不會錯。
- **只往前不往後**：後台寫入一律取較大者（`greatest`）；用戶端合併也取較大者。舊設備晚送、重送、亂序都不會倒退。
- **對話鍵**（`ui/lib/read-sync.mjs` 的 `readKey`，電腦與手機同一個函式）：夥伴 ID（`p_…`）優先；沒有就 `n:節點/名字`（與封存同一套寫法；總機是 `n:節點/`）；群組 `g:群組代號`。
- **一個動作**：`read_sync`，一次呼叫「送出我這端待送的已讀位置（可空）＋取回整個帳號的」。節流後打一次就完成回寫與合併，不必拆成讀、寫兩個動作。
- **本人簽章**：沿用 `x-asn-user`（登入憑證）。沒簽章 401、完全不打資料庫；簽章的人要擁有呼叫節點（`asn_user_owns_node`）。AI 視窗拿得到節點金鑰，但拿不到登入憑證，所以改不了已讀。

## 用戶端行為（`AsnCore`，電腦與手機共用）

1. `markRead`（開啟對話、切到對話、回前景）：把已讀位置推到該對話最後一則收到的信，記進待送清單。位置沒前進就不動作。
2. 對話開著時收到信：當場視為已讀並記進待送清單。
3. 節流：記錄後等 3 秒才送，連讀多位只打一次。
4. 取回：每次名單刷新（約 60 秒）與啟動時順便呼叫一次，取回別台的位置，合併後把未讀消掉：已讀位置之後還有幾則收到的信，未讀就剩幾則（只讀一部分就只消一部分）。
5. 收到比已讀位置舊（或相等）的信（別台已經讀過）：不算未讀。
6. 離線：失敗時待送清單留著，下次補送；待送清單也存在本機存檔（`readDirty`），重開後仍會補送。
7. 沒登入：Rust 端在打後台之前就回錯，前端靜默，行為與以前完全相同。登入後自然開始同步。

## 相容

- 舊後台：對沒見過的動作回 404，新端靜默退回本機行為，這次執行不再問。
- 舊用戶端：不會送也不會讀，完全不受影響；新後台只是多一個動作與一張表。
- 沒有 `readSync` 的 transport（舊測試、其他殼）：整段略過。

## 後台

- migration `20261023080000_read_sync.sql`：資料表 `relay.read_marks(user_id, key, read_at, updated_at)`，RLS 開且不建 policy；函式 `public.asn_relay_read_sync(p_actor, p_signed_user, p_marks)`（新名，不需要舊名包裝），security definer、search_path 空、只授權 service_role。
- 防呆：一次最多 100 筆；壞一筆整批不寫；時間夾在「現在＋5 分鐘」內；每帳號最多 2000 個鍵（只擋新增）；90 天沒更新的順手清掉（信件也只留 90 天）。
- Edge Function：`_shared/read_sync.ts`，`relay/index.ts` 只對 `read_sync` 讀簽章標頭。
- 守門測試 `rpc_names_test.ts`：原本要求每個 `asn_relay_*` 名稱都在改名 migration 的清單裡；新函式一開始就叫新名，所以放寬為「在清單裡，或在改名之後的 migration 直接建立」。

## 部署順序

migration → relay 函式 → 發新版 ASN。反過來也安全：新端遇到舊後台 404 就靜默退回本機行為。

## 沒做的

- 群組（`g:` 鍵）：鍵與後台已支援，但群組畫面還在另一條線開發中，等它的未讀進 `AsnCore` 後，在群組標已讀處呼叫同一個 `#advanceRead` 即可。
- 即時推播：目前最慢約 60 秒（名單刷新）才看到別台的已讀；要更快可在回前景時多呼叫一次 `syncReads()`。
