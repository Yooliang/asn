# 遠端一次性密碼傳遞（#26 第二期）

目標：別台電腦（或雲端代理）上的程式要密碼時，請求在**你本人的設備**（電腦 ASN 或手機）上跳出確認；你輸入的密碼以端對端加密送回請求端；收發室與後台只轉密文，看不到原文。

這一期接在第一期（本機一次性傳遞，見 [SECRETS.md](SECRETS.md)）後面，沿用同一個確認窗與同一種「交給要密碼的程式」的方式（印到標準輸出）。第三期（保管箱）與第四期（能不用密碼就不用）見 SECRETS.md。

## 一眼看懂

```
請求端（雲端代理／另一台電腦）                 後台                       本人的設備（電腦 ASN／手機）
 1 產生一次性鑰匙對（私鑰只在記憶體）
 2 secret_request：公鑰＋程式＋用途＋有效期限 ──▶ 記一筆（只有公鑰）──敲門鈴──▶ 3 secret_pending（本人簽章）
                                                                              4 跳窗：哪台電腦、哪個程式、要做什麼、公鑰指紋
                                                                              5 你輸入密碼 → 用請求公鑰加密
                                               ◀── secret_reply（本人簽章）密文 ──┘
 6 secret_fetch（輪詢）◀── 密文（只能取一次，取走即清）
 7 解密成功 → 印到標準輸出給要密碼的程式 → 立刻銷毀私鑰與明文
```

## 流程細節

1. **請求端**（`secret_remote::requester`）：產生一次性 X25519 鑰匙對。私鑰是密碼學套件的「臨時私鑰」型別：**不能序列化、不能複製、解密時被消耗掉**，所以不可能被寫到檔案或 log，用完（或請求失敗、逾時、被丟棄）就沒有了。
2. **請求**：`secret_request`，內容只有公鑰（43 字元 base64url）、程式名稱（≤80 字）、用途說明（≤200 字）、有效期限（30～600 秒，預設 180）。請求編號由後台產生。請求端節點一定要「有主人」（節點與租戶都屬於同一個登入帳號），沒綁帳號的設備不能請求——否則沒有人能替它確認。後台敲**本人其他設備**的門鈴（不敲請求端自己）。
3. **本人設備查待確認**：`secret_pending`，**一定要本人簽章**（登入憑證，AI 視窗拿不到）。只回「公鑰與說明」，不含任何密文；只回這個登入帳號自己設備發起的、尚未過期的請求。
4. **確認窗**：顯示三件事——**哪台電腦**（後台依請求節點查出的設備名稱，不是請求端自報）、**哪個程式**與**用途**（請求端自報，標示為「對方自報」）、**公鑰指紋**（公鑰 SHA-256 前 8 碼，如 `3fa9-c21e`；請求端在標準錯誤也印出同一個指紋，高風險情境請兩邊核對）。倒數到請求期限。可按取消＝拒絕。文字顯示前一律清理（控制字元、雙向文字控制碼、超長）。
5. **加密**：在**本人設備本機**做。用請求公鑰與一把新的臨時鑰匙對做 ECDH（X25519）→ HKDF-SHA256 導出 256 位元金鑰 → AES-256-GCM 加密。密文格式見下。
6. **回覆**：`secret_reply`（本人簽章）送密文。後台只做格式檢查（長度、字元集）就存起來，敲請求端的門鈴。
7. **取回**：請求端 `secret_fetch` 輪詢。**密文只會被取走一次**：取走的同一個動作把後台的密文清成空值、狀態改成「已送達」。第二次取只回狀態。
8. **解密與交付**：請求端用私鑰解密。**解密失敗（金鑰不對、被竄改、編號對不上、長度不對）一律不交付任何東西**，回錯誤；成功才把明文交給要密碼的程式（印到標準輸出，與第一期小幫手同一種方式）。私鑰在解密那一刻被消耗，明文用完立刻清零。

## 密碼學（全部用現成套件，不自己發明）

- 套件：`ring`（本來就在 ASN 的相依樹內：X25519、HKDF-SHA256、AES-256-GCM）。
- 金鑰協議：X25519，雙方都是一次性金鑰（請求端的在記憶體、本人設備的是加密當下產生的臨時鑰匙）。共用秘密全零（低階點攻擊）一律拒絕。
- 金鑰導出：HKDF-SHA256；salt＝請求編號的 16 位元組；info＝`"asn-secret-v1" ‖ 請求編號 ‖ 請求公鑰 ‖ 臨時公鑰`。
- 加密：AES-256-GCM，隨機 12 位元組 nonce（金鑰每次不同，不會重用）；附加驗證資料（AAD）＝`"asn-secret-v1" ‖ 請求編號`。
- 明文：`2 位元組長度 ‖ 密碼 ‖ 補零`，固定補到 1026 位元組，**密文長度不洩漏密碼長度**。密碼上限 1024 位元組。
- 密文格式（base64url，無補齊）：`版本(1)=1 ‖ 臨時公鑰(32) ‖ nonce(12) ‖ 密文＋驗證標籤`，共 1087 位元組、1450 字元。
- 因為請求編號與請求公鑰都放進金鑰導出與 AAD，**為甲請求加的密無法在乙請求解開**；重放別人的密文給別的請求會解密失敗。

## 綁定、有效期限、一次性、重放保護

| 規則 | 怎麼做（後台函式 + 用戶端） |
|---|---|
| 綁請求編號 | 編號進金鑰導出與 AAD；取回只認「請求端節點」＝金鑰所屬節點，別的節點（連本人的別台）都取不到 |
| 幾分鐘有效 | 30～600 秒（預設 180）；過期不能回覆、不能取回、不顯示在待確認；確認窗的倒數與期限一致 |
| 一次性（回覆） | 只有「等待中」且沒過期的請求能被回覆；第二次回覆（含先答應再拒絕）一律「已回覆過」 |
| 一次性（取回） | 取走即清空密文，第二次只回「已送達」 |
| 重放保護 | 公鑰唯一（同一把公鑰不能開第二個請求）；請求端的臨時私鑰用過即毀；舊密文帶到新請求解不開 |
| 頻率限制 | 每台設備同時最多 3 筆等待中、每小時最多 20 筆 |
| 自動清 | 每個動作開頭先清：過期／已取走／已拒絕的密文立刻清成空值；過期一小時後整列刪除（留一小時讓請求端查得到「已過期」） |

## 密文與原文不去的地方

- **後台資料表**：只有公鑰、說明、密文（取走或過期就清空）。沒有原文，也沒有任何私鑰。
- **信件／往來記錄**：整個流程**不走信件**：請求與回覆是獨立的動作與資料表，不經 `relay.messages`，不進往來記錄、不進群組。
- **log**：Edge Function 資料庫出錯時只記函式名與錯誤代碼，**不記錯誤物件**（約束違反的詳細內容會帶整列資料，包含密文）；電腦與手機端的 log／錯誤訊息只含動作名與狀態碼；守門測試掃描這一點。
- **門鈴**：只敲主題，不帶內容。

## 本人簽章才能回覆

`secret_pending` 與 `secret_reply` 沿用「本人簽章」（`x-asn-user` 標頭，值是登入憑證）。AI 視窗拿得到節點金鑰，拿不到登入憑證：

- 沒簽章：Edge Function 直接 401，不打資料庫；
- 簽章有效：資料庫再核對「簽章的人擁有**回覆的設備**」與「**請求端節點**」且租戶是他的。別人的簽章、別租戶、節點金鑰洩漏的情況都回覆不了；
- 簽章的使用者代碼只取自驗證後的憑證，不收請求內容裡自報的。

## 威脅模型與誠實限制

| 威脅 | 防護 | 殘餘風險（誠實寫出） |
|---|---|---|
| 後台／收發室被攻破、資料庫被讀 | 只有公鑰與（短暫存在的）密文；密文沒有請求端私鑰解不開；私鑰從不離開請求端記憶體 | 攻擊者可**拒絕服務**（不轉、丟請求）；可看到「誰在何時要過密碼」的中繼資料（設備名、程式、用途、時間）——這是確認窗需要的資訊，無法隱藏 |
| 後台**換掉公鑰**（中間人）：把請求裡的公鑰換成自己的，本人加密給攻擊者 | 確認窗顯示公鑰指紋，請求端在標準錯誤印同一個指紋，請人核對 | 不核對就擋不住。這是「後台可信」假設的邊界：本期的保證是**被動竊聽與資料外洩**（讀庫、讀 log）看不到原文，**主動竄改的後台**需要靠指紋核對。高風險情境請務必核對 |
| 請求端**那台機器**上的惡意程式 | 私鑰只在記憶體、解密後立刻銷毀 | **擋不住**：同一使用者底下的惡意程式能讀行程記憶體、能攔截標準輸出（與第一期同一限制）。若請求端被入侵，遠端傳遞不比本機更安全 |
| AI 冒用名義請求密碼 | **每次都要你本人在自己的設備確認**，確認窗寫明設備、程式、用途；請求端只能「請求」，沒有任何不經確認取得密碼的路 | AI 仍可「請求」（它能叫程式發請求），也能亂編程式名稱與用途；最後一道防線是你看清楚再按。程式與用途是**請求端自報**，不可信，只有「設備名稱」來自後台 |
| 騷擾式洪水請求 | 每台同時 3 筆、每小時 20 筆、確認窗排隊 | 仍會跳窗；你可以隨時取消，之後可加更嚴的頻率限制 |
| 重放舊回覆／別的請求的密文 | 見「綁定」表 | — |
| 本人設備上的惡意程式 | 與第一期同 | 擋不住（同一使用者的記憶體讀取、螢幕錄影、鍵盤側錄） |
| 未登入／登入憑證過期 | 沒憑證不送請求回覆，畫面提示先登入 | 手機與電腦都要登入才能確認 |
| 密碼長度洩漏 | 固定補零到 1026 位元組 | — |
| 網頁引擎／系統暫存裡的明文 | 盡力清零 | 與第一期同：WebView 輸入欄、行程間通訊暫存、換頁檔我們清不到 |

## 元件與位置

- 後台：`supabase/migrations/20261023060000_secret_remote.sql`（資料表 `relay.secret_requests`、函式 `asn_relay_secret_purge／request／pending／reply／fetch`）；`supabase/functions/_shared/secret_remote.ts`（格式檢查、簽章把關、錯誤對應）；`supabase/functions/relay/index.ts` 分派四個動作 `secret_request／secret_fetch／secret_pending／secret_reply`。
- 電腦與手機共用的 Rust：`relay/asn/src-tauri/src/secret_remote/`——`crypto.rs`（加解密）、`wire.rs`（後台往來的輸入整理）、`requester.rs`（請求端）、`confirm.rs`（確認端：查待確認→跳窗→加密→回覆）。
- 請求端的指令列：`asn-cli secret request --purpose <說明> [--program <名稱>] [--ttl <秒>]`，成功只把密碼印到標準輸出；失敗訊息在標準錯誤、標準輸出為空（`GIT_ASKPASS` 包裝腳本可以直接呼叫它）。
- 電腦確認端：沿用第一期的確認窗（`askpass.html`），多顯示「請求設備」與「公鑰指紋」；ASN 收到門鈴後自動查待確認並跳窗。
- 手機確認端：手機版畫面的「⋯」選單旁的密碼請求面板（`m.js`），指令 `android_secret_pending／android_secret_reply`；加密在 Rust 端，畫面只拿到說明與傳回「是否成功」。

## 守門測試（每條都做過還原驗證）

- 後台（deno）：沒簽章 401 且不打資料庫；簽章者與節點取自驗證結果；資料庫出錯時 log 不含密文／公鑰／說明；原始碼只有一行 console；門鈴不帶內容。
- 後台（pglite 實跑）：非本人簽章不能回覆、別人的請求回不了、重複回覆被拒、過期被拒、取走後密文清空與只能取一次、別的節點取不到、拒絕不留密文、公鑰唯一、頻率上限、過期自動清。
- Rust：加解密來回；錯的私鑰／被改一位元／換請求編號／換公鑰／低階點都解不開；解密失敗**不交付**；私鑰用完即消耗（型別層面）；密文與原文不出現在 log／往來記錄／任何後台明文欄位（假後台收到的所有請求都掃描）；確認端取消＝回拒絕。

## 已知限制與之後可做

- 只做「密碼／通行片語」一種，上限 1024 位元組；沒有檔案或權杖的格式。
- 公鑰指紋核對是人工的。第三期（保管箱）可改成裝置配對時一次性交換信任根（類似 Signal 的安全碼），之後不必每次核對。
- 沒有「記住這個程式 30 分鐘」的白名單（屬第三期與 #23）。
- 請求端目前只有 `asn-cli`（Windows／Linux 的 Rust 程式）；Node 版的收發室橋與雲端代理腳本（`relay/cloud-agent`）還沒有對應的請求指令，建議第三期補一個純 Node 的請求端（Node 內建 X25519／HKDF／AES-GCM，同一份密文格式）。
- 手機尚未支援當請求端。
- 後台沒有排程清理（靠每個動作開頭順手清）；沒人用時過期的列會留到下一次有人呼叫為止（密文也是），可在第三期加定時清理。
