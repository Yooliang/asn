# 系統通知集中成一個「通知」對話（#848，0.2.13）與手機通知分頁（#895，0.2.14）

狀態：設計草稿，等小良哥回覆群組 #3413 的 7 題後定案。依據 main `8f935812` 的盤點（asn40，2026-11-07）。
第五節的幾題尚待小良哥定案，文中先照 asn真 的建議寫，定案後再改。

## 一、問題

- 系統通知現在各用一個寄件名。後台（SQL 函式）寄的有：
  - 登入通知收發室
  - 收信監控收發室
  - 額度通知收發室
  - 轉交核對收發室
  - 等待確認收發室
  - 終端服務收發室
  - 雲端設定收發室
  - 看畫面收發室
- 每台電腦的橋另外用 `<節點>-收發室` 寄「找不到視窗」「先留著」「額度扣住」「轉交失敗」這類通知。
- 用戶端（電腦和手機共用 `ui/lib/core.mjs` 的 `#incoming`）遇到沒見過的寄件人，會用 `routing.mjs` 的 `stubFriend` 建一列聯絡人。狀態寫死成 offline，而且會一直留著。所以名單上多出好幾個「離線」對話，看起來像夥伴。
- 「不回信」的判斷靠寄件名結尾是「收發室」，或內文開頭是 `[收發室]`。這個判斷散在 Rust 橋、Node 橋、雲端代理、UI 大約 15 處（見附錄）。

## 二、目標

1. 每個帳號只有一個「通知」對話，電腦和手機都一樣。
2. 每則通知的第一行寫明「哪一台：什麼事」。設備用顯示名，不用節點代號；沒有名字時沿用 `UNNAMED_DEVICE` 的寫法。
3. 「通知」對話不顯示上線狀態，也不能回信（沒有輸入列）。
4. 不回信改看「這封是不是系統通知」，不再看名字結尾。
5. 舊版用戶端在過渡期內不壞：照樣收到舊寄件名，行為和現在一樣。

## 三、做法

### 3.1 怎麼認出系統通知

- **固定的寄件人**：`from_agent = 'ASN 通知'`。`from_node` 照舊用「出事的那台」，或後台的系統節點，讓舊用戶端照舊能顯示。
  - 名字裡不含「收發室」。過渡期內，舊用戶端會把它當成一位新聯絡人，所以要等新版普及後才切換（見 3.4）。
- **新增信件類別** `kind`（文字，可以是 null）：
  - 系統通知帶 `notice:<種類>`，例如 `notice:login`、`notice:quota`、`notice:mux_down`、`notice:waiting`、`notice:view`、`notice:node_mismatch`、`notice:bridge`。
  - 一般信件是 null。
  - 用戶端判斷是不是系統通知：先看 `kind` 開頭是不是 `notice:`；沒有 `kind` 時，再看寄件人是 `ASN 通知`，或名字結尾是「收發室」（相容舊信）。
  - 要不要加 `kind` 欄位需要改資料庫，見 3.3。如果不加，就只能靠固定寄件人判斷，不能分種類。建議加，手機分頁的篩選和未讀數之後都會用到。

### 3.2 用戶端（PR-B，先發版）

- **共用判斷**：新增 `ui/lib/notice.mjs`，提供 `isSystemNotice(mail)`，供 `core.mjs`、`text.mjs`、電腦和手機的畫面使用。
- **Rust 和 Node 橋**：`is_mailbox_sender` 改名成 `is_system_notice`，判斷「`kind` 是 `notice:*`、或寄件人是 `ASN 通知`、或名字結尾是『收發室』」。呼叫點照舊。內文開頭 `[收發室]` 的判斷也保留。
- **雲端代理**（`config.mjs:92,124`、`grok-agents.mjs:52`）也做同樣的改動。
- **`core.mjs` 的 `#incoming`**：遇到系統通知不建 stub 好友，一律放進固定的對話 `notice:<帳號>`，畫面上顯示成「通知」。
  - 舊的「○○收發室」對話第一次載入時就併進「通知」：往來記錄依時間合併，未讀數相加。舊的那幾列不再顯示。
  - 本機的原始資料先不刪，留一版以便回復。
- **「通知」對話的畫面**：沒有上線狀態圓點、沒有輸入列、沒有通話鈕。名單固定排在最上面，或放在獨立分組，這一點等定案。
- **電腦和手機一致**：都走 `core.mjs`，所以不用另外改。

### 3.3 後台（PR-C，等新版普及才上）

- **共用函式**：新增 `public.asn_relay_send_notice(p_node text, p_kind text, p_body text)`。
  - 收件人是節點的擁有者，寄件人固定是 `ASN 通知`，`kind` 寫成 `notice:<p_kind>`，不能回信。
  - 限流改成看「節點＋種類＋1 小時」，不再看寄件名。改了寄件名，限流也不會失效。
- **各通知函式**：約 10 支（附錄列出 migration 檔名）改成呼叫這支共用函式。內文第一行一律寫「<設備顯示名>：<什麼事>」。
- **`relay.messages` 加 `kind` 欄位**：文字，可以是 null，不加預設值，舊資料是 null。Edge 收信時把它原樣帶給用戶端。舊用戶端不認得這個欄位，會直接忽略。
- **舊信**：已經存在 `relay.messages` 的舊寄件名信件不動，用戶端照 3.2 的規則併進「通知」。
- **不可逆的點**：PR-C 上線後，還沒更新的舊版用戶端會看到一位新聯絡人「ASN 通知」。所以要等 PR-B 發出去 7 天（待定案）之後才上；上線前用在線回報確認大多數設備都已經是新版。
- **回復**：`asn_relay_send_notice` 照舊保留，各通知函式改回原本的寄件名就能回復。`kind` 欄位可以留著不刪。

### 3.4 橋自己寄的通知（PR-D，可以和 PR-C 同一版）

- 寄件人從 `<節點>-收發室` 改成 `ASN 通知`，`kind` 帶 `notice:bridge`，第一行寫明哪一台。
- 這批通知是寄給夥伴視窗的，夥伴那邊同樣靠 `is_system_notice` 判斷不回信。所以要等 PR-B 那一版的橋普及之後才切換。

### 3.5 手機通知分頁（#895，0.2.14，PR-H）

- **第四格固定是「通知」**：`TABS` 改成四個，內容就是 3.2 的「通知」對話。
- **設定暫時佔用第四格**：
  - 在第三頁點「設定」時，第四格暫時換成設定頁。
  - 離開超過 3 分鐘（待定案）後，跳回「通知」，取代現在的「收起」。
  - 雲端金鑰還在畫面上時延長到 30 分鐘，「離開前先問」，這兩個現有行為都保留。
- **直達入口**：設定裡加一個「看通知」的入口。
- **未讀紅點**：第四格顯示未讀紅點（待定案）。
- **不要撞名**：設置裡現有一個叫「通知」的分類，是震動設定（`mobile-settings.mjs:9` 的 `notify`）。這個分類要改名成「提醒」或「震動與提醒」，避免和新分頁同名。

## 四、PR 拆法與順序

1. **PR-A**：這份設計文件。
2. **PR-B**：用戶端同時認得新舊兩種寄件人，加上「通知」對話。不動後台，發版。
3. **PR-C**：後台改用共用寄通知函式，加 `kind` 欄位，限流改看種類。動資料庫，等 PR-B 普及後才上。
4. **PR-D**：橋自己寄的通知換新寄件人。可以和 PR-C 同一版。
5. **PR-H**（0.2.14）：手機通知分頁。

（#832 一個節點多個 bot、#746 舊名轉投，另見 #832 的計畫。#832 的「雲端設定」通知直接用 PR-C 的共用函式。）

## 五、待小良哥定案（群組 #3413）

以下先照 asn真 的建議寫：
- 整個帳號一個「通知」對話。
- 舊的「○○收發室」對話自動併進「通知」。
- 後台在新版發出去 7 天後才換寄件名。
- 「通知」對話不顯示上線狀態，也不能回信。
- 第四格沿用 3 分鐘逾時，加未讀紅點。
