## 1. 目前 ASN 架構概要

ASN 目前可視為兩條核心，外加周邊功能直接寫在主程式裡。

### 1.1 傳訊核心（messaging relay）

負責信件收發、帳號、節點、金鑰、門鈴、群組。金鑰只留在 Rust 行程記憶體；前端／插件層不應拿到。後台存信後只對收件節點按門鈴（不帶內文），收件端再拉信、確認、顯示。

### 1.2 終端主控核心（terminal control）

負責攔截各家 AI agent 的畫面、輸出、輸入來控管。Windows 自 0.2.4（#830）起：

- ASN 主程式與終端服務是**兩個不同行程**。終端服務是 ASN 拉起的獨立 WezTerm 伺服器終端（mux），不是內嵌在主程式裡。
- 每位 AI 夥伴是自己獨立的程式，各佔服務裡的一個窗格。
- **一位夥伴崩潰，不影響其他夥伴**；若終端服務本身掛掉，裡面所有窗格會一起斷（共用的代價）。
- 關掉、重開或更新 ASN，夥伴仍在服務裡跑；ASN 回來後可認回並接上。

Linux／macOS 在 0.2.4 維持原狀（要明確設定才會開 mux）；Linux 終端服務的目標版號見 **PLUGIN-PLAN**（撰寫本文件時曾寫 0.2.9，後已顺延）。

### 1.3 周邊目前怎麼放

開新夥伴、廠商整合、設定頁、推播等目前多半直接寫在主程式／中樞檔案裡，還沒有正式的插件邊界。

## 2. 插件化方向（建議）

**兩個核心先不拆成插件，保持不動，但把對外介面定清楚。**

插件若要讀畫面或送按鍵，只能走核心的權限檢查（例如「視窗不在前景就不送」這類守門），不能直接碰金鑰或 inbox／ack 協定。

### 2.1 適合拆成插件的

| 區塊 | 為什麼適合 | 介面粗略方向 |
|---|---|---|
| **廠商整合**（Claude、Gemini、agy、grok 等） | 各家差異最大、變動最頻繁 | 怎麼啟動、怎麼認權限框／選項框、怎麼回答、怎麼判斷結束或登入失效 |
| **推播／通知管道**（Firebase、門鈴延伸、系統通知） | 管道可替換 | 「送一則通知給本人」→ 成功／失敗 |
| **平台差異**（Windows／Linux／macOS 開窗與程序管理） | Linux 與開窗差異適合抽介面；**承接版號見 PLUGIN-PLAN**（`PlatformHost`） | 開窗、程序生命週期、服務安裝／接回 |

### 2.2 比較不適合當獨立插件的

- **設定頁、開新夥伴流程**：較適合讓每個插件**自帶設定欄位**，由主程式統一顯示。
- **傳訊核心、終端主控核心**：安全與穩定底線，不插件化。

### 2.3 試做順序（概念；版號以 PLUGIN-PLAN 為準）

依 **2026-11-06 方案 B 決議**與 **2026-11-07 版表拍板**（#935、#937），插件化自 **`PLUGIN-PLAN` 的 0.2.18** 起一版一事，**不重排**其間已規劃的終端／FCM 等功能版（見 §7）。下列為討論時定的**工作內容**；各版對照見 **`docs/design/PLUGIN-PLAN.md` §3.1、§10**：

1. **拆前端 `transport`**（`mailTransport`／`desktopExtras`）並凍結 AsnCore 傳輸契約——**PLUGIN-PLAN：0.2.18**。
2. **廠商適配**：把 **認畫面**、**判斷結束**、**判斷登入失效** 等收進「一家一個適配器」；討論時以 Claude 為典型起點，**計畫版表為先 agy（0.2.19）、Claude 最後（0.2.22）**，細節以 PLUGIN-PLAN 為準。
3. **通知管道**、**平台介面**——版號見 PLUGIN-PLAN（勿在此重複寫死）。

## 3. 對話功能現況（程式碼，`4810e5b`）

對話這塊**已經半套件化**；真正的問題是中樞太胖，以及傳輸介面塞了太多東西。

### 3.1 怎麼組織

| 層 | 位置（相對倉庫） | 觀察 |
|---|---|---|
| 電腦版中樞 | `relay/asn/ui/list.js` | 約 1889 行、約 80 個匯入；收信、名單、開窗、設定、終端、群組都綁在這裡；AsnCore 在此跑 |
| 對話窗 | `relay/asn/ui/chat.js` + `relay/asn/ui/lib/chatpane.mjs`（ChatPane 約 526 行） | 只負責顯示與發事件，**不碰網路**（檔案註解也這樣寫） |
| UI 函式庫 | `relay/asn/ui/lib/` 約 131 個 `.mjs` | 含 `core.mjs`、`roster.mjs`、`groups.mjs`、`group-flow.mjs`、`room-hub.mjs`、`markdown.mjs` 等 |
| 手機 | `m.js` + `mobile-*.mjs` | 與電腦共用 AsnCore／ChatPane |
| Rust 網路 | `src-tauri/src/relay.rs`（約 2033 行） | 金鑰只留在 Rust 記憶體 |
| 前端 transport | `lib/tauri.mjs` 的 `transport` | 約 50 個方法，**混了**收發信、終端、啟動、語音 |
| 後台 | `supabase/functions/relay/index.ts` + `_shared` 的 rooms／groups／partners／attachments | 存信、門鈴、群組叫醒等 |

**寄信流程：** ChatPane 發出寄信事件 → AsnCore → `transport.send` → Rust `relay_send` → 後台存好 → 只對收件節點按門鈴（不帶內文）→ 收件端拉信、ack、顯示。

**群組：** 用一個「假夥伴」塞進好友名單，共用同一個對話窗。

### 3.2 適合再拆／不該拆

**適合拆成套件／模組的：** Markdown 顯示、ChatPane、群組流程畫面、名單呈現、附件預覽。

**不該當插件的：** 金鑰與簽章、本人／成員信任判斷、`expects_reply`、AsnCore 的 inbox／ack／去重／已讀協定、後台門鈴／群組叫醒／權限 RPC、終端主控。

### 3.3 介面草圖

- **傳訊核心（AsnCore 用）：** `list()`／`inbox()`／`ack()`／`send()`（外加 history／readSync／sendAttachment 等信件相關）。
- **ChatPane：** 只收 `friend`／`me`／`log` 這類 props；只發出 `send`／`nudge`／`attach`／`group-*` 事件。
- **群組套件：** 不碰 inbox ack。
- **名單套件：** 不自己發 HTTP。

### 3.4 插件化起步（討論結論；版號以 PLUGIN-PLAN 為準）

**2026-11-06** 討論定案內容（方案 B、行為不變）包含兩類工作：

2. **廠商適配：** 把分散的 **認畫面**、**判斷結束**、**判斷登入失效** 收斂成「一家一個適配器」；討論當日曾構想以 Claude 為第一個完整樣本。

## 4. DeepSeek Harness（dsh）調查結果

### 4.1 是什麼

DeepSeek 開源的 agent 執行層，指令 `dsh`，約 2026-08 公開預覽，MIT 授權。官方提醒仍是 developer preview，之後可能有不相容變更。口號是 **「Everything is a Plugin」**，底層用 **Cordis** 插件框架。

模型、工具、技能、對話紀錄、沙盒、檔案系統、agent 主迴圈、介面都可以換成別的插件。

### 4.2 插件機制摘要

- **載入：** 設定檔（profiles）+ bundles + `cordis.patch.yml` 一層層疊成插件樹；也可用 `dsh plugin add`／`remove`。
- **生命週期：** 插件註冊服務、型別化事件、可收回的作用；卸載時全部收回。
- **擴充縫：** 介面（interface）＋提供者（provider）＋使用者（consumer）。
- **工具：** 執行前有攔截鏈。
- **權限兩軸：**
  1. **審批（approval）：** 預設要問人；沒人回答就**拒絕**（fail-closed）。
  2. **沙盒：** 唯讀／只能寫工作區／完全開放。
- **MCP：** 一台伺服器一個插件實例（工具名形如 `mcp__server__tool`）。
- **終端：** `ctx.terminals` 可當可替換的提供者。

### 4.3 值得 ASN 參考的點（設計概念，不是採用整套）

1. 兩個核心先不拆，但對外把介面（seam）定清楚。
2. 權限框的回答者做成可插拔鏈，**預設拒絕**。
3. 各家廠商做成「一家一個適配插件」。
4. 可疊加的設定（profile／patch），適合小步快跑。
5. 終端可當成可替換提供者，但**執行與審批仍走核心**。

## 5. 大方向提案：二選一比較（初步）

| 面向 | **(A) dsh／Cordis 當宿主骨架**，ASN 傳訊與聊天窗掛成插件，使用者只看 ASN 介面 | **(B) ASN 自建輕量插件系統**，兩個核心不動，只定對外介面 |
|---|---|---|
| 控制權 | 受制於上游預覽與 Cordis 生命週期 | 完全自控 |
| 金鑰安全（Rust） | 插件同進程共享 Context；金鑰要進 Node 或再加 IPC，攻擊面變大（見 §6） | 金鑰繼續只留 Rust；插件永遠不碰金鑰 |
| 手機支援 | 官方幾乎沒有嵌進 Tauri／Android 的路（推斷） | 沿用現有 Tauri 2 + Vue 3 + Android |
| 上游風險 | developer preview、可能不相容、未過安全稽核 | 無此依賴 |
| 短期成本 | 換殼層／事件／打包，幾乎重寫（推斷） | Claude 適配＋拆 `transport`／契約，成本可控 |
| 看到收益的速度 | 慢（先付遷移債） | 快（插件化自 PLUGIN-PLAN 所訂起點，見 §3.4） |
| **決議（2026-11-06）** | **不採納當底層** | **小良哥拍板採方案 B**；可借用 dsh 的設計概念；Gemini審查（PR #894）同意不採 dsh 當宿主 |

比較表為決策前評估；**細節與落地順序見 §3.4、§7、§9 與 PLUGIN-PLAN**。

## 6. Harness 作為底層的可行性評估

**總評：現階段不建議用 dsh／Cordis 當 ASN 底層骨架，可當插件化設計參考。**

理由：

1. **技術棧不合。** dsh 是 Node／TypeScript，官方桌面是 Electron；ASN 是 Tauri 2 + Vue 3 加 Android。官方沒有嵌進 Tauri 或手機的路：要麼雙行程（Tauri + Node sidecar），要麼整換 Electron（**推斷**）。
2. **傳訊核心放進插件層風險高。** dsh 插件同進程共享 Context；其 SAFETY 相關說明寫插件可碰憑證、檔案、網路。傳訊核心放進去，金鑰就要進 Node 或再加一層 IPC，攻擊面變大。其 approval 擋的是**工具執行**，不是 ASN 的節點金鑰模型。
3. **產品面不合。** dsh UI 插件對準 agent 對話串流，不是信件。要藏起 agent loop，等於關掉 dsh 大半產品面，卻仍扛 preview 風險。ChatPane 已是純顯示＋事件，應繼續當 ASN 自己的 UI 模組。
4. **排程衝突。** 換宿主會重做殼層、事件、打包；0.2.5～0.2.13 幾乎全擋或重寫（**推斷**）。
5. **成熟度。** dsh 仍是 developer preview、會有不相容變更、未過安全稽核；手機幾乎沒官方路徑。

**過渡路線（依方案 B 決議）：**

- **不採納** dsh 當宿主（Gemini審查於 PR #894 結論一致）。
- **借用概念：** 介面＋提供者＋使用者、工具前攔截、預設要問／失敗關閉——用在終端權限與廠商整合。
- **先做什麼、哪一版做：** 見 **`docs/design/PLUGIN-PLAN.md`**（0.2.18 transport／契約；0.2.19 起廠商適配；Claude 三類判斷收斂見該檔 Claude 章節）。本討論文件不另列版號。
- **以後若碰 Cordis：** 只評估「某一家 agent 引擎適配」當**可選外掛**；**永遠不碰金鑰與 inbox／ack**。

## 8. 風險

1. **介面定太早會綁住後面。** 契約要小、可擴充，但不要一次定死十年。
2. **插件權限＝潛在後門。** 若插件能讀畫面／送按鍵／讀信，等於開後門。規則：**插件永遠不碰金鑰**；讀畫面／送鍵必須走核心權限檢查。
3. **測試變多。** 每個插件都要有自己的實機驗證，可能拖慢發版。
4. **短期重構看不到新功能。** 要控制在「行為不變、只改匯入」的小步。
5. **手機＋電腦共用核心**（推斷／現況）：改一次兩邊都要重測回歸。
6. **群組是假夥伴**（推斷）：硬拆時未讀／已讀容易出錯；群組套件不要碰 inbox ack。
