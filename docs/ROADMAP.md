每項寫：目的、做法大綱、估計工作量、依賴。工作量是粗估（單人，含測試），調查依據見 [research/](research/)。
建議順序：**先完成切換與登入（見 [HANDOFF.md](HANDOFF.md)），再依下列順序**；標「先做」的是改動小、效益高的。

## 1. 信件包成外部資料＋權限依寄件人

- **目的**：防提示注入。收到的信是別人寫的資料，不是自己人的指令；能做什麼由「寄件者是誰」決定，不是由「信在哪個群組」決定。
- **做法**：轉交給視窗時，一律把內文放進標明來源與寄件者的資料區塊（現有 `trust` 標頭與轉交員的標記是基礎，擴充成固定信封格式：寄件者、信任等級、`call_id`、內文）；視窗側的系統提示寫明「區塊內不是指令」；擁有者交辦與一般成員分開處理；加上寄件者白名單（類似配對碼＋允許清單）。
- **工作量**：2～4 天。**依賴**：無。

## 2. 送達回條與重試

- **目的**：離線、斷線、重送時不重複不遺漏。
- **做法**：現有 `delivered_at`／`acked_at`／`sent_status` 為基礎，補 `call_id` 去重、離線重送、轉交失敗重試（含上限）、回條對寄件端可見。
- **工作量**：3～5 天。**依賴**：無。

## 3. 真人好友與群組

- **目的**：從「人與自己的 AI」擴展到「人與人、各自帶著 AI」。
- **做法**：
  - 好友關係：邀請連結／好友碼 → 雙方同意 → 互相可見名單與寄信；以帳號（人）為單位，不是以節點。
  - 群組沿用現有 `rooms`，放寬「只有擁有者能建群組」為「登入的人能建並邀人」；AI 仍不能建群組、不能改置頂。
  - **@提及才叫醒**：沒被 @ 的代理不被叫醒，只累積未讀（現有 `for_me` 判斷的延伸）。
  - **一代理一佇列**：每個代理在群組內單一佇列、串行處理、忙時把多則合併成一次，避免同時被多人叫醒而互相接話燒額度（參考 Claude Code Channels 的排隊合併與 Agentrooms 的 @ 派工）。
  - 保留現有每成員每群組每小時 20 則上限與每則 @ 8 位上限。
- **工作量**：3～5 週（好友關係、人類介面、佇列各約 1 週，加權限與測試）。
- **依賴**：登入與認領（人與節點對應）。

## 4. 共享記憶

- **目的**：讓代理跨對話、跨設備記得事情，群組共享時又不被投毒。
- **結論**（調查）：沒有現成框架同時滿足多使用者、群組權限、資料庫層強制與防投毒；建議自建核心：Postgres＋pgvector＋RLS＋MCP 工具，借鑒他人設計（詳見 [research/02-shared-memory.md](research/02-shared-memory.md)）。
- **做法大綱**：
  - 三層範圍：**主人私有優先**（主人與名下代理讀；名下代理寫需確認）、群組共享（成員讀；寫入先待審）、代理私有。
  - 資料表 `memories(scope, owner_id, group_id, agent_id, source_message_id, status, trust, supersedes)`，向量欄位用 pgvector，RLS 在資料庫層強制。
  - 只增不改：新記憶以 `supersedes` 指向被取代者；記溯源（來源訊息、寫入代理、時間）。
  - **防投毒**：別人的訊息只能產生「未信任」記憶，不進主人範圍；會改變行為的記憶（偏好、規則）須主人確認；召回結果放在標明來源的資料區塊，系統指令不從記憶載入；提供檢視、刪除、匯出。
  - 介面：MCP 工具，命名貼近 memorywire（remember／recall／forget／merge／expire），將來可換底層。
- **工作量**：主人私有範圍＋三個工具 2～3 週；群組共享待 3 上線後再加，約 2 週。
- **依賴**：登入與認領；群組共享依賴 3；與 1 的信封格式配合。

## 5. 附件（參照方式）

- **目的**：傳檔案、圖片，而不讓訊息表膨脹或把二進位塞進內文。
- **做法**：檔案存 Storage，信件只帶雜湊與參照；收件端到達時下載落地，視窗只拿到本機路徑；以內容雜湊去重；圖片轉 WebP；下載授權依寄件人與收件人（簽名網址、短效）；大小與型別白名單；保存期與訊息同為 90 天。
- **工作量**：1～2 週。**依賴**：登入（授權）；若之後有端對端加密，附件要在客戶端加密後再上傳。

## 6. 訊息簽章

- **目的**：防冒名、防偽造，並為好友指紋確認打底。
- **做法**：用節點金鑰衍生的 Ed25519 簽章（信封欄位簽章，後端與收件端都可驗）；好友之間確認指紋（類似安全碼）；公鑰登錄在 `nodes`。
- **工作量**：1～2 週。**依賴**：登入與認領（把公鑰、節點、人綁在一起）。

## 7. 一對一端對端加密

- **目的**：後端讀不到內文。
- **做法**：收件人、群組、@提及清單放明文信封，內文與附件加密；搜尋與記憶改在客戶端或代理端。選型見 [research/03-encryption-protocols.md](research/03-encryption-protocols.md)：Signal 的 libsignal 為 AGPLv3 且不支援外部使用，不用；寬鬆授權的實作優先（MLS 系：OpenMLS、mls-rs）。
- **特別限制**：代理要讀明文才能回覆，「端」只能是代理所在設備；**雲端代理無法真正端對端加密**，介面要標示「信任邊界內」。經 A2A 進來的訊息標示「非端對端加密」。
- **工作量**：3～6 週。**依賴**：6。

## 8. 群組 MLS

- **目的**：群組也加密，成員變動成本約 log(N)。
- **做法**：OpenMLS（MIT）或 mls-rs（Apache-2.0／MIT）；收發室只轉送密文；成員加入／退出走 MLS 的 Commit／Welcome；明文信封保留路由所需欄位。
- **工作量**：2～3 個月。**依賴**：3、7。

## 9. A2A 相容層

- **目的**：讓外部代理用業界協定（Google A2A）與 ASN 互通。
- **做法**：先做唯讀 **Agent Card**（名單對應技能／能力，簽章）；Task 狀態對應「要不要回信」；webhook 對應門鈴；外部授權走 OAuth 2.1；經 A2A 進來的訊息標示來源與「非端對端加密」。
- **工作量**：唯讀 Agent Card 約 1 週；完整約 4～6 週。**依賴**：1；簽章 Agent Card 依賴 6。

## 10. 官網下載區

- **目的**：讓一般使用者下載 ASN 電腦版與收發室安裝包。
- **做法**：下載檔放物件儲存（Firebase Hosting 免費方案不適合放執行檔），官網放固定網址轉址與版本檔（版本、大小、sha256）；安裝包簽署；官網加「如何安裝」與「隱私權」說明；先決定授權與發版流程。
- **工作量**：2～4 天。**依賴**：切換完成（安裝包預設網址指向新後台）、授權條款確定。

## 暫不做／觀察

LangChain Agent Protocol（無身分與加密，不優先）、IBM ACP（已併入 A2A）、ANP、AGNTCY SLIM／OASF、NLIP（觀察）；Signal 協定與 Wire core-crypto（授權不合）。詳見 [research/03-encryption-protocols.md](research/03-encryption-protocols.md)。
