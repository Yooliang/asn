# 團隊流程（開 PR、審查、合併、發版）

ASN 由幾個 AI 夥伴分工開發。這份文件整理出已經踩過坑才定下來的規則，每條都附上來源（群組編號或 PR）。

分工（小良哥 2026-10-27 群組 #506 定）：
- **asn小東**：帶隊，負責分工、追進度、更新藍圖。
- **asn西川**：開發、合併、發版。
- **Gemini審查**：外部審查。
- **ASN-開發**：會議召集人。

## 開 PR
- 每個 PR 和每份審查報告都要寫**完整的 commit SHA**（40 碼）。後來又推了新 commit，就重貼新的 SHA，舊的核可不算數。
- 沒在真機上看過的畫面，要在 PR 裡寫「沒在真機看過」，並列出還沒驗證的項目。
- 測試要一個檔一個檔跑，不要一次丟整批，整批跑會卡住。根目錄的 tests 用 `tools/run-root-tests.mjs`（#314）。

## 審查
- 至少要一位 Gemini審查 或 asn小東 核可，而且核可的 SHA 必須等於 PR 現在的 head（小良哥 #388：審查過、大家同意後就可以合）。
- **終端送字、代答這類 PR**（`term_send`、`term_answer`、`term_remote_*`）：審查報告裡要單獨寫一段「逐條走過每一種結束方式」，不能省。共六種：電腦確認、手機確認、手機拒絕、過期、取消、換分頁。每一種都寫出之後畫面和後端會變成什麼樣，寫完才給結論。
  - 來源：#329、#330、#334 三次都是審查通過後才發現漏洞，見群組 #598、#599。
- 會改到安全預設的變更，要在群組寫清楚，等小良哥同意。
- 一個 PR 的審查結果合成一則發，不要連發好幾則。

## 合併
- **疊在別的 PR 上的 PR**（目標分支不是 main），合併前要先把目標分支改成 main，或先合被疊的那個 PR，再把這個 PR 改成以 main 為目標。目標分支沒改就合下去，只會進到舊分支，主線完全沒動。
  - 來源：#291 疊在 #290 上，10/26 16:00 會議記錄；#334 疊在 #332 上，群組 #604。
- 合完要在 PR 留言寫合併後的 SHA。

## 發版
- 由 asn西川 發版。順序是：桌面版、安卓官網版、Play、官網部署。
- **藍圖要跟著發版同步**：每次發版後，asn小東 要在同一天開一個 PR，把 `site/public/roadmap.html` 的待辦和版本狀態更新到最新版。改完重跑 `node site/make-roadmap-page.mjs`，它會從 CHANGELOG 和 `site/meetings.json` 產生頁面。
  - 來源：藍圖落後過好幾次，見 #297 與 10/27 12:00 會議。
- 會議記錄只要在 `site/meetings.json` 加一筆就好。不用管排序，產生器會依時間把最新的排在最上面。

## 群組
- 群組每小時最多 20 則。回報合成一則，只在被點名或真的需要時才回。
- 群組裡只寫 issue 或 PR 的編號加一兩句結論，細節寫在 issue 或 PR 裡（群組 #531、#532）。
- 盤點、調查這類工作要指名給一個人做，不要好幾個人各做一份（10/27 的頭像盤點同時出了 #333、#335、#336 三份）。

## 不可以做的事
- 不直接推送到 main；只有 asn西川 合併。
- 不碰線上後台（Supabase）；migration 由 asn西川 套用。
- 做了就收不回來的事，要由小良哥決定。例如：倉庫公開、花錢、刪資料。
