# 自動發佈運行手冊

對應程式：`tools/release/auto_publish.mjs`（判斷規則在 `tools/release/auto_publish_core.mjs`）。來源：#1980、#2003。

## 1. 用途

常駐程式每隔一段時間（預設 120 秒）查 GitHub 上的發版 run：

- 電腦版 `asn-release.yml`（標籤 `v<版號>`）
- Linux 版 `asn-release-linux.yml`（標籤 `linux-v<版號>`）

某一版打包全綠就先試跑一輪（dry-run），下一輪再正式發佈，實際工作由 `tools/release/local_sign_publish.mjs` 做。Linux 一定等同版電腦版發完才會跑。失敗不會自動重試，也不會繼續發更新的版本，要人工處理。

所有相對路徑與子程序（git、gh、node）都以 repo 根目錄為基準，不受啟動目錄影響。`--state` 若給相對路徑，會以啟動目錄解析成絕對路徑，並在 log 寫一行實際使用的路徑。

## 2. 第一次上線

1. 開一個專用的 git worktree（程式會拒絕在主 checkout 執行），切到最新的 origin/main。
2. 在該 worktree 的 `relay/asn` 跑 `npm ci`。正式發佈那步要用簽章相依（`relay/asn/node_modules/@tauri-apps/cli/tauri.js`），缺了會回報「準備失敗」。
3. 播種：先不加 `--yes` 執行 `node tools/release/auto_publish.mjs --seed <線上版號>`，程式會印出兩平台最新成功的 run 版號和線上 latest.json 版號，以及播種計畫。確認無誤後加上 `--yes` 才會寫入。起點低於線上版會被拒絕（會重發舊版）。兩個平台版號不同時用 `--seed-desktop <版號>` 與 `--seed-linux <版號>`。
4. 先用 `--dry-run-only` 常駐觀察：只會跑試跑，遇到待正式發佈的就只寫 log，不會真的發佈。確認 log 與群組訊息都正常。
5. 去掉 `--dry-run-only`，正式啟動。

## 3. 常駐方式（建議）

用工作排程（Windows 工作排程器）在登入或開機時啟動，工作目錄設為專用 worktree：

```
node tools/release/auto_publish.mjs --room <群組代號>
```

- 不帶 `--once` 就是常駐，每 `--interval` 秒一輪（不得小於 10 秒）。
- 帶 `--once` 只跑一輪就結束，可改成工作排程每幾分鐘觸發一次。
- `--room` 是回報訊息要貼的群組；不給就只寫 log，不貼群組。
- 程式自己會取鎖，重複啟動不會重複發佈。

## 4. 資料夾裡的檔案

預設放在 `%LOCALAPPDATA%\asn-auto-publish\`（取不到時用使用者家目錄），可用 `--state <檔>` 改位置。下列檔案都和 state 同一個資料夾：

| 檔案 | 用途 |
| --- | --- |
| `state.json` | 發佈紀錄：播種起點、每個版本的結果、執行中的標記。損壞或結構不對時程式不覆寫、不發佈。 |
| `state.json.lock` | 鎖。內容是「pid、毫秒時間戳」。鎖超過 2 小時、或 pid 已不存在，會被當成殘留自動接手。 |
| `state.json.notices.json` | 去重用：同一類回報只貼一次（準備失敗類別、state 壞掉、gh 連續失敗計時）。只有持鎖者會寫。 |
| `state.json.blocked-since-<pid>` | 被鎖住時記「從何時開始被擋」，每個程序只寫自己 pid 的那份，取到鎖後會自己清掉。程式沒在跑時若看到殘留，可直接刪。 |
| `post-pending.json` | 待貼佇列（格式見下方「待貼佇列」）。 |
| `post-pending.json.lock` | 待貼佇列自己的鎖，格式同 `state.json.lock`，只在讀改寫的一瞬間持有。 |
| `post-pending.json.bad-<時間>` | 待貼佇列讀不懂時改名留下的原檔。 |
| `post-pending.json.rejected-<時間>` | 待貼佇列中不合格的單筆另存的檔。 |
| `post-pending.json.lock.bad-<時間>` | 待貼佇列壞鎖改名留下的原檔。 |
| `auto-publish.log` | 全部過程紀錄，包含子程序的 stdout、stderr 原文。群組只貼固定文案，細節都在這裡。 |

## 5. 回報訊息與處理

| 訊息（大意） | 意思 | 怎麼處理 |
| --- | --- | --- |
| 自動發佈被鎖住超過 30 分鐘 | 鎖被另一個程序佔住（可能是正在跑的發佈、也可能是 `--seed` 或 `--ack`）。鎖超過 2 小時會被當殘留接手。 | 看 log 的 pid，確認那個程序是否還活著、是否在做事。真的卡死就結束該程序，鎖會自動被接手。 |
| 連續 30 分鐘查不到 GitHub 上的發版狀態 | gh 一直失敗（登入失效、網路、額度被限）。恢復後計時自動清掉並寫 log。 | 在這台機器上確認 gh 登入與網路。修好後不需要其他動作。 |
| 準備失敗，尚未發佈：<原因> | 跑發佈之前整理工作樹失敗（fetch 失敗、標籤衝突、工作樹有其他改動、site 檔與 main 不一致、缺相依等）。不進 state，下一輪會再試，同一原因只貼一次。 | 依原因處理：缺相依就在 `relay/asn` 跑 `npm ci`；工作樹髒就整理乾淨。細節看 log。 |
| state 檔讀不懂或結構不對 | state 不是合法 JSON，或缺必要欄位。程式停止處理、不覆寫原檔。 | 停掉程式，從備份還原，或依第 8 節手動修補。修好後恢復，不需其他動作。 |
| 自動發佈還沒有播種 | state 存在但沒有合法的起點。不會發佈任何東西。 | 依第 2 節播種；state 已存在時 `--seed` 會拒絕，改依第 8 節補 `since`。 |
| 有未處理的失敗，暫停自動發佈 | 有一筆失敗類紀錄還沒確認，電腦版與 Linux 版都停。 | 處理完那一筆失敗後用 `--ack`（見第 6 節）。 |
| `<平台@版號>`：打包流程沒有成功 / 試跑失敗 / 正式發佈失敗 | 對應步驟失敗，不會自動重試。 | 看 log 與 local_sign_publish 的輸出，人工處理完再 `--ack`。 |
| Linux 等人工處理，不會自動發佈 | 同版電腦版沒發成，Linux 被標為 blocked。 | 電腦版處理完後，`--ack linux@<版號>`。 |

## 6. 何時要用 `--ack`

`--ack <平台@版號>` 把一筆失敗類紀錄標為「人工已確認」，確認後才會恢復處理新版本。只准清失敗類（打包失敗、試跑失敗、正式發佈失敗、逾時、blocked），對已發佈或播種的紀錄會報錯。它會取鎖，程式正在跑發佈時會被拒絕，稍後再試。

重點：

- **電腦版自動那條失敗、改走備援手動發版之後，一定要對那一版下 `--ack desktop@<版號>`。** 手動發版不會寫進 state，沒有確認的話，電腦版與 Linux 版的新版都會一直暫停。
- **Linux 被標 blocked 時**（同版電腦版沒發成），電腦版處理完後要 `--ack linux@<版號>`。
- 任何失敗訊息處理完，都要 `--ack` 對應的那一筆。

範例：

```
node tools/release/auto_publish.mjs --ack desktop@0.2.45
```

`--ack` 與 `--seed` 不能同時給。

`--ack <平台@版號>` 成功時，告警檔（`alert.json`）裡 ref 是同一個「平台@版號」的 active 告警會一起標成已恢復，其他版本的告警不動。

### 只清一類告警：`--ack-alert <類別>`

告警本身已經處理、但那一類告警還掛著時（例如人工補貼完群組後清掉 `post-failed`），用 `--ack-alert` 只清那一類，不動 state：

```
node tools/release/auto_publish.mjs --ack-alert post-failed
```

- 類別只認 `post-failed`、`already-running`、`bad-state`、`gh-failed`、`prep-failed`、`pending-bad`，其他字會報錯。
- 取鎖方式和 `--ack` 一樣（不取常駐單例鎖）；程式正在跑發佈時會被拒絕，稍後再試。
- 該類別目前沒有 active 告警時，只回報「沒有需要清的告警」，不算錯。
- 不能和 `--ack`、`--seed` 同時給。

### 發佈成功但群組沒貼成（#2345）

常駐程式不在 Claude 視窗底下執行，asn-cli 依設計拒絕寄信，所以發版最後一步「貼群組」可能貼不出去。這時發佈本身（Release、官網、版本紀錄）都已完成、結果照記「已發佈」，不會暫停後面的發佈；但會在告警檔（`alert.json`）留一筆 active 的 `post-failed`：

- `ref` 是那次的「平台@版號」（例如 `desktop@0.2.99`、`linux@0.2.99`）。
- 訊息裡附了要人工補貼的原文，照貼到群組即可。同一版電腦版與 Linux 都沒貼成時，兩個平台的原文會累加在同一筆告警裡（同一則不重複），不會互相蓋掉。
- 下一輪沒有東西要貼時不會自動清掉；只有人工清除，或之後真的有一則群組訊息貼成功時才會標成已恢復。

人工補貼完之後清掉它：

```
node tools/release/auto_publish.mjs --ack-alert post-failed
```

已發佈的版本不是失敗類，`--ack <平台@版號>` 不收；請用 `--ack-alert post-failed`。

### 打包偶發失敗、重跑變綠，但常駐程式已記成處理過

情境：某版電腦版打包 run 偶發失敗（例如冒煙測試偶發），常駐程式已把 `desktop@<版號>` 記成打包失敗、`linux@<版號>` 記成 blocked，寫進 `state.json` 的 `done`。之後對同一個 run 用 gh 只重跑失敗的 job（`gh run rerun <runId>` 加上 failed 選項）重跑變綠，常駐程式也不會再發，因為 `done` 裡已有這兩筆；main 沒有新改動時，release-tag 也不讓打下一版。

處理步驟：

1. 確認重跑真的全綠，而且原本失敗的那個情境這次是過的。同一個情境又紅就不是偶發，停下回報，不要改走手動發版。
2. 先 `--ack` 這兩筆（若還沒）：`--ack desktop@<版號>`、`--ack linux@<版號>`。確認 `state.json` 的 `pending` 為空、`inflight` 為 null。
3. 停常駐程式：對排程下 `Stop-ScheduledTask`，並只停它自己的 PID（不要全機砍 node）。確認 `state.json.lock` 不在。
4. 把 `state.json` 備份到同資料夾，檔名帶時間，例如 `state.json.bak-YYYYMMDD-HHMMSS`。
5. 編輯 `state.json`，只刪 `done` 裡 `desktop@<版號>` 和 `linux@<版號>` 兩筆，其他不動。
6. 用 diff 對備份，確認只少這兩筆、JSON 仍合法。
7. 重啟排程，看 log 確認它接手並對該版開始試跑（dry-run）；之後照常正式發佈，Linux 跟著發。
8. 發完照平常收尾（群組通知、官網版本紀錄等）。

範例：v0.2.102 的 run 45741060307 就是這樣處理的（冒煙測試 m-photo-zoom 偶發，見 issue #2357）。

### 待貼佇列（post-pending.json）

位置：與 `state.json` 同一個資料夾。格式：

```
{ "v": 1, "updatedAt": "<ISO 時間>", "items": [
  { "id": "desktop@0.2.99#published", "kind": "published", "platform": "desktop", "version": "0.2.99",
    "commit": "<8 位小寫 hex>", "at": "<ISO 時間>", "createdAt": "<ISO 時間>", "attempts": 0,
    "lastError": null, "claimedBy": null, "claimedAt": null } ] }
```

- 每一筆只有上面這些固定欄位，沒有文案、沒有群組代號。
- `id` ＝ `平台@版號#kind`；同一筆重複寫入只留一筆。
- `kind`：`published`（已發佈、通知沒貼成）、`ci-failed`、`blocked`、`dryrun-failed`、`publish-failed`（同名回報沒貼成）。
- `lastError`：`null`，或同時符合「100 個碼點以內」「加引號跳脫後 160 位元組以內」「不含 Unicode 類別 Cc、Cf、Zl、Zp、Cs 的字元」的字串，不合格整筆拒絕；寫入前用 `cleanLastError` 處理（拿掉上述字元，並以完整碼點為單位截斷）。只寫進待貼檔給人排錯，不得出現在群組文案或代貼指令的輸出。
- `platform` 只能是 `desktop`、`linux`；`version` 是三段數字、每段最多 6 位（`0.2.99`）；`commit` 是 8 位小寫 hex（寫入端只收剛好 40 碼的 SHA，取前 8 碼）。
- `at`、`createdAt`、`claimedAt` 要與 `toISOString()` 往返一致；`attempts` 為 0 到 1000 的整數；`claimedBy` 為 0 到 4294967295 的整數。
- 欄位固定、型別固定；多出欄位、型別不對、單筆超過 512 位元組，整筆拒絕。
- 讀到或要寫入的每一筆都先驗格式，不合格整筆丟掉並記 warn（只說哪個欄位不合格）；讀檔時同一個 `id` 只留第一筆。
- 讀寫都在 `post-pending.json.lock` 內進行；鎖檔時間戳在未來超過 5 分鐘、或內容讀不懂，視為壞鎖，改名為 `post-pending.json.lock.bad-<時間>` 並留 `pending-bad` 告警；改名後重讀隔離檔，與改名前讀到的不同就還原並放棄這一輪。拿不到鎖或寫入失敗只記 log，不影響發版結果。
- 檔案大小先用 stat 檢查；整個檔讀不懂或超過 64 KB 時改名為 `post-pending.json.bad-<時間>`，留一筆 `pending-bad` 告警，不覆寫。
- 檔案讀得懂、只有部分筆不合格：合格的留在佇列，不合格的另存為 `post-pending.json.rejected-<時間>`，留一筆 `pending-bad` 告警（訊息帶筆數）。
- 佇列滿了（超過 50 筆或超過 64 KB）：新的一筆不寫入，留一筆 `pending-bad` 告警；人工處理佇列後再用 `--ack-alert pending-bad` 清除。
- `pending-bad` 告警：程式任何地方都不會自動標成已恢復，只能用 `node tools/release/auto_publish.mjs --ack-alert pending-bad` 人工清除。
- 目前只負責寫入；告警的行為不變。

各類回報與告警的處理分工：

| 類別 | 處理方式 | 要人處理時怎麼清 |
| --- | --- | --- |
| `published` | 進待貼佇列，由代貼處理 | `--ack-alert post-failed` |
| `ci-failed` | 進待貼佇列，由代貼處理 | `--ack <平台@版號>` |
| `blocked` | 進待貼佇列，由代貼處理 | `--ack <平台@版號>` |
| `dryrun-failed` | 進待貼佇列，由代貼處理 | `--ack <平台@版號>` |
| `publish-failed` | 進待貼佇列，由代貼處理 | `--ack <平台@版號>` |
| `prep-failed` | 只亮固定句，要人處理 | 處理好後自動恢復；`--ack-alert prep-failed` |
| `stale` | 只亮固定句，要人處理 | `--ack <平台@版號>` |
| `paused` | 只亮固定句，要人處理 | `--ack <平台@版號>`（清掉造成暫停的那筆失敗） |
| `unseeded` | 只亮固定句，要人處理 | `--seed <版號> --yes` |
| `gh-failed` | 只亮固定句，要人處理 | gh 恢復後自動恢復；`--ack-alert gh-failed` |
| `bad-state` | 只亮固定句，要人處理 | `--ack-alert bad-state` |
| `locked` | 只亮固定句，要人處理 | 鎖釋放後自動消失；沒有清除指令 |
| `already-running` | 只亮固定句，要人處理 | `--ack-alert already-running` |
| `pending-bad` | 只亮固定句，要人處理 | `--ack-alert pending-bad` |

## 7. 怎麼停止

1. 結束常駐的 node 程序（工作排程就停用或結束該工作）。只結束自己記下 pid 的那一個，不要整批結束 node。
2. 確認 `state.json.lock` 消失；殘留的話，鎖的 pid 已不存在就會被下次啟動自動接手，也可以手動刪。
3. 停用工作排程，避免被再次拉起。
4. 想暫時不發佈、又要繼續觀察，就改用 `--dry-run-only` 重啟。

停止期間的新版本不會遺失：下次啟動會從 state 的紀錄繼續。

## 8. 刪掉整個資料夾等於放棄保護

「曾經跑過」的痕跡（`auto-publish.log`、`state.json.lock`、`state.json.notices.json`）和 state 放在同一個資料夾。state 不見但痕跡還在時，程式拒絕啟動，避免誤刪 state 後重複發佈舊版。

**把整個資料夾刪掉，這層保護就沒有了**：程式會把它當成全新安裝。要重新使用，必須用 `--seed <版號> --yes` 重新播種。播種會對照線上 latest.json，起點低於線上版就拒絕，所以不至於重發舊版，但舊的失敗紀錄與確認記錄都會消失。不要為了清 state 而刪整個資料夾。

### since 壞掉時手動補（#2003 單上提到）

`since` 是播種起點。state 的 `seeded` 為 true 卻沒有合法的 `since`（手改過、寫到一半）時，程式當成沒播種，不會發佈任何東西。state 已存在時 `--seed` 會拒絕，所以要手動補：

1. 先停止程式（第 7 節），確認鎖已消失。
2. 備份 `state.json`。
3. 查線上 latest.json 的版號，以及 `state.json` 的 `done` 裡兩平台已處理的最大版號。
4. 編輯 `state.json`，把 `since` 補成 `{ "desktop": "<版號>", "linux": "<版號>" }`，版號格式必須是 `x.y.z`，且不低於線上版，也不低於 `done` 裡已處理的版本；確認 `seeded` 為 true。
5. 存檔後重新啟動，先用 `--dry-run-only` 觀察一輪。

`since` 以下（含）的版本一律視為已處理，填太低會讓舊版被重新發佈，填太高會漏發中間的版本。
