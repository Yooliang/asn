# ASN 0.2 細部拆解規畫（Gemini審查 / 審查與架構視角提案）

> 依據：小良哥群組 #973 指示「0.2 版各家 AI 都能從 ASN 完整管理：經『內建通道（ACP）』或『經 pi』開得起來、關得掉、能切模型、能改名、能接手自己開的 pi；活躍度跨設備；去 Irori 化完成、舊後台停用清掉」。
> 本份文件由 **Gemini審查（家用機）** 提出，專注於**安全邊界、權限守門、狀態一致性、行程生命週期防護（防止殘留孤兒）、資料遷移安全**與**可驗證的里程碑推進**。

---

## 零、核心目標與四大基石原則

0.2 版的產品承諾是「各家 AI 納入同一管理體系」。從系統架構與審查角度，必須嚴格守住以下四大原則：

1. **最小特權與邊界明確（Least Privilege & Explicit Boundaries）**：
   - 啟動與接手 AI 時，不跨出授權白名單（`allow_dirs`、`write_dirs`）；ACP 與 pi 行程各自受限，不私開未授權 RPC 管道。
2. **行程生命週期乾淨閉環（Zero Zombie Processes）**：
   - 關閉與切換模型時，嚴格清理行程樹（使用現有 `kill_set` 機制向下遞迴清理子孫行程），防止孤兒進程長期佔用系統資源或背景偷跑。
3. **記憶與識別不失憶（Session & Identity Continuity）**：
   - 改名、重啟、切換模型時，以 Session ID / 內部識別碼為錨點，維護對話歷史與交接檔案（`HANDOFF`）的一致性，不可因改名導致工作者被當作新夥伴重新初始化。
4. **不可逆動作的漸進與護欄（Progressive & Guarded Sunset）**：
   - 去 Irori 化與舊後台退役涉及資料與相容性中斷，實施「資產搬遷先行 → 唯讀監測 → 零使用驗證 → 正式停用 → 移除相容層」的階段式護欄，非經主人明確確認絕不執行破壞性指令。

## 二、六大工作線細部拆解與安全防護規格

### 工作線 A：經 pi 通道全生命週期打通（最優先，覆蓋多數非 Claude 模型）
1. **A1. pi 程序的優雅與強制關閉（Stop）**：
   * **規格**：選單提供「關閉」。優先發送 IPC / 控制檔結束請求；若 3 秒內未退出，觸發 `switch::kill_process_tree` 強制殺死該 pi 及其子程序。
   * **安全護欄**：嚴格檢查目標 PID 是否屬於 ASN 啟動之實例，絕不誤殺使用者原有的終端機或 ASN 本身。
2. **A2. 接手自己開的 pi（#240，方案 B 接線）**：
   * **規格**：將 `pi_adopt.rs` 接上 UI「納入管理 / 接手」操作。
   * **隱私守門**：掃描對話目錄僅解析 session id 與對話第一行摘要（驗證合法性），嚴禁讀取內部私鑰或敏感對話內容。
3. **A3. pi 忙碌切模型排隊佇列**：
   * **規格**：修改 `control.mjs` 與橋端協定，當 pi 處於忙碌狀態（`busy`）時，將切換請求標記為 `pending`，待當前回合（turn）結束後自動套用，取代目前的同步等待逾時（Timeout）。
4. **A4. pi 夥伴改名（Rename）**：
   * **規格**：改寫 `~/.asn/pi-windows.json` 與名單映射，通知 UI 更新，Session ID 保持不變。

### 工作線 B：ACP 內建通道管理完善（Gemini / Grok）
1. **B1. ACP 改名實作（#266 收尾）**：
   * **規格**：實作 `AcpAdmin::rename`，驗證新名稱合規性（`^[A-Za-z0-9_-]{1,40}$`），原子性改寫 `agents.json` 與 session 映射表，廣播改名通知更新 UI 與通訊錄。
2. **B2. ACP 雙軌關閉機制**：
   * **規格**：提供「停止本次執行」（暫時釋放資源，有信件來時可再拉起）與「停用並移除」（自名單與設定檔移除）。
   * **安全護欄**：清理行程時同步回收 ACP 通道監聽，避免端口或管道殘留。
3. **B3. ACP 模型動態切換**：
   * **規格**：選單支援切換模型；底層透過重寫 `agents.json` 的 `model` 欄位並重啟工作者行程，重啟時利用 `session/load` 接續歷史對話，確保「對話不中斷、模型即時切換」。

### 工作線 C：Codex 視窗管理接線
1. **C1. 接線啟用 `codex_ops.rs`**：
   * **規格**：將既有已編譯通過之關閉、切模型邏輯接上前端夥伴選單與 RPC 橋。
2. **C2. 雙機真機驗證**：
   * **規格**：驗證帳號切換、模型切換與行程關閉之穩定性。

### 工作線 D：手機與多端體驗對齊
1. **D1. 手機開新夥伴四選一升級**：
   * **規格**：手機開新夥伴頁面同步電腦版，支援「內建通道」與「經 pi」選項。
2. **D2. 遠端開 pi 參數傳遞**：
   * **規格**：後端 `launches` 資料表擴充 `provider` 與 `model` 欄位，支援手機遠端命令家用機/工作機啟動指定模型的 pi。

### 工作線 E：活躍度跨設備精確同步（#397）
1. **E1. 後端 `last_active_at` 與節流寫入**：
   * **規格**：在後端加入節點/夥伴最後活動時間戳；發信、回信、群組發言時自動觸發。
   * **頻率限制保護**：本地節流（至少 10 秒內不重複推送純活動更新），防止 Supabase 負載過高。
2. **E2. 四色燈號跨設備一致性**：
   * **規格**：各端讀取遠端活躍時間戳，一致顯示綠色（活躍）、黃色（閒置 > 5 分鐘）、紅色（離線 > 30 分鐘）或灰色（封存）。

### 工作線 F：去 Irori 化與舊後台退役安全推進（#14）
1. **F1. 下載資產遷移（前置必備）**：
   * 將安裝檔與更新檔全面自 `irori.web.app/download` 搬遷至 `asnmessenger.web.app`，更新 `build_downloads.mjs`。
2. **F2. 呼叫計量與零使用驗證（Observability）**：
   * 上線舊版環境變數與舊版 API 呼叫計數報表，確認所有在線節點已零呼叫。
3. **F3. 舊後台唯讀與下線（需主人核准）**：
   * 停止舊 Supabase 專案寫入；停用舊 Edge Functions。
4. **F4. 程式碼與 DB 相容層收斂**：
   * 移除 `supabase/sql/` 舊檔與舊包裝函式；更新程式內所有常數名稱。相容期依小良哥拍板之時程執行。

## 四、待小良哥決策建議（審查建議案）

針對領隊 asn真 提列的決策項目，Gemini審查提供以下建議方針供小良哥裁定：

1. **內建通道（Gemini、Grok）關閉模式**：
   * **建議**：**支援雙軌**。預設「關閉」為「停止執行並釋放資源」（有信件時可再拉起），選單另提供「解除安裝 / 移除此夥伴」。
2. **內建通道切換模型之重啟延遲**：
   * **建議**：**完全可接受**。因底層 ACP 為長生命週期程序，改寫 `agents.json` 後重啟並自動載入原 Session，延遲約 2~3 秒，但架構最穩定、程式碼改動最小且最不容易發生狀態競爭。
3. **#241 雲端節點多夥伴叫醒歸屬**：
   * **建議**：**移至 0.3**。0.2 應全力收斂本機與跨端之管理功能，避免戰線擴大。
4. **舊後台退役時機**：
   * **建議**：資產搬遷完成且連續 7 天監測報表確認舊後台零流量後，先改為唯讀 1 週，無異常即正式下線。
5. **舊名相容期長度**：
   * **建議**：新代碼一律全面改用新名；相容層可精簡保留至確認無舊版用戶端活躍（監控為零），不強制死守 90 天，以實測數據為準。
6. **#300 設備間互信（免確認）**：
   * **建議**：0.2 先維持現況（方案 A：有本人簽章免確認、無簽章需確認）。待 0.3 人與人或更完整的設備授權協議建立後，再一併放寬。

## 五、審查核對清單（Checklist for Reviewers）

- [ ] **權限合規**：新增的遠端操作與命令，必須嚴格遵守 `write_dirs` / `allow_dirs` 白名單限制。
- [ ] **行程安全**：所有關閉邏輯必須經過 `taskkill` / `kill_process_tree` 雙層檢查，不留孤兒程序。
- [ ] **資料防護**：改名與接手流程不傳遞明文金鑰，對話歷史透過標準 Session API 存取。
- [ ] **相容平滑**：舊後台退役過程提供緊急復原路徑（Fallback URL / Read-only 備份）。
