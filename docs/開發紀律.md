# ASN 開發紀律

> 這份是 ASN 所有開發夥伴（人與 AI）都要照做的規則。寫 PR、審 PR、發版前，照這份逐條對。
> 由來：2026-11-19 一天之內，擁有者撞到好幾個「修過又復發」「手機和電腦不一樣」「壞了卻沒有提示」的問題。擁有者的原話：「不是我說一條改一條吧，自己制定規則與紀律」。
> 規則有改，直接改這份，PR 標題寫「紀律：」開頭。
> **流程規則只有這一份。** 2026-11-27 起，`docs/TEAM-FLOW.md` 與 `docs/版本規劃.md` 原本各寫一份的規則都併進來了；其他文件提到流程規則時只准指向這裡，不准另寫一份（守門測試會擋）。

## 零、規則怎麼立（2026-11-27）

由來：11-27 盤點發現規則「寫了卻沒用」的三個原因：規則寫成給人讀的字、同一條規則散在三份文件而且互相矛盾、沒有人量它有沒有被遵守。有守門測試的地方（事件、設定值、日誌）都收斂了，沒有的（通知、文件、舊實作）都繼續各長各的。

1. 規則只有兩種形式：**機器擋**（守門測試或 CI 檢查，違反就紅燈）和**靠人**（寫明誰在什麼時候查）。新規則寫進這份文件時，同一張 PR 要在文末「規則對照表」登記是哪一種。
2. 能寫成守門的就寫成守門。靠人的規則被違反第二次，就開單把它改成機器擋。
3. 規則、清單、對照表這類「唯一來源」都要有守門測試確認它沒過期（例如表上寫的檔案真的存在、清單和程式對得上）。沒有守門的清單，過幾天就不能信。
4. 動手前先查 [唯一出口](唯一出口.md)：要做的事表上有出口，就一定走那個出口，不准另寫一份；新增一類共用出口，同一張 PR 登記進去。
5. 規則之間有衝突時，先停下來問領隊，由領隊改這份文件；不要自己挑一條照做。

## 一、一份畫面，三個平台

1. 手機、電腦、網頁共用同一份功能、同一份介面元件和同一份樣式。三邊只有「版面」可以不同（電腦雙欄、手機先清單再內容、網頁同電腦），另外就是平台本來就沒有的功能（系統匣、推播、Play 更新、右鍵、長按）。
2. 不准做出某一邊獨有的樣子：新畫面或新樣式三邊一起做，要不然就都不做。做的順序（擁有者 2026-11-27 定）：先用設計稿或網頁版給擁有者確認，再延伸到電腦與手機；延伸可以分開做，但都掛在同一張母單底下，全部做完這張單才算完成，不准只做一邊就收。
3. 使用者看得到的文字只放一份常數，三邊都從那裡引用，不准在 `m.html`／`list.html` 各寫一次。
3-1. 同一條規則（例如誰算在線、誰能改名、額度怎麼算）只能有一個函式實作，所有入口都呼叫它。11-06～11-19 的 19 組復發裡，有 7 組是「規則寫死在好幾處」，是最大宗。
4. 修毛病之前，先找有沒有其他「兄弟副本」：用症狀關鍵字搜手機和電腦兩邊，PR 說明寫出搜了什麼、找到哪幾處。只修其中一處，就等於留了一個復發。

## 二、修毛病：從根因修，留下守門測試

1. 先找到根因再動手。只修顯示、不修根因的，要在 PR 和給擁有者的回報裡講明「根因沒修」。
2. 每個修正都要附一支回歸測試，而且要證明「拿掉修正會紅燈」。PR 說明寫出測試名稱。
3. 測試用真資料或真路徑。例如畫面要吃的是後台存的那份資料，就拿資料庫裡實際存的那份當輸入，不准自己造一份剛好會過的假資料（#1126 的教訓）。
4. 只修壞掉的那條路。正常運作的功能不要順手加守門、不要順手改流程；看到的延伸問題另外開單。
5. 修過又復發的問題，加上「復發」標籤。修的時候一定要加一支以單號命名的守門測試（例如 `test('#1803 設備名稱只有一個來源', …)`）。
6. 復發不靠人記得貼標籤：PR 範本檢查會比對主線歷史，**同一張單修過、發過版、現在又修，就算復發**，要寫「復發單號：#單號」並附守門測試；確定不是復發，就在 PR 說明寫「不是復發：原因」，審查的人要看這一句。

## 二之一、收斂與退場（2026-11-27）

由來：10-23 就決定機器橋只維護 Rust 一份，但切換沒有人負責、也沒排進開發順序，Node 版一直留著；11-27 還有一張改動把同一套規則再寫一次進 Node 版（程式約 1,100 行、測試約 1,000 行）。

1. 決定用新的取代舊的那一天，就把舊的登記進 [退場清單](退場清單.md)：誰取代它、誰負責到刪掉為止、什麼條件下刪。
2. 登記之後舊的只修不加：不新增檔案、行數不增加，守門測試會擋。修正真的要多寫幾行時，同一張 PR 調高基準並寫原因。
3. 新功能只做在取代它的那一邊。單上寫「兩邊都要」「跟某某版同一套」而另一邊正在退場時，先停下來問領隊，不要照抄一份過去。
4. 負責人要負責到舊的刪掉為止。部署、試跑、切換、觀察這類工作不適用「每項 30 分鐘」，但一樣要排進開發順序、有單號。
5. 同一件事已經有兩份實作、而這張單會讓它變成三份時，先開單把它收成一份，再做功能；擁有者明講先做的除外。收斂的單怎麼排，照第九之一節（能不能排在功能單前面還待擁有者確認）。

## 三、不准靜默失敗

1. 失敗一定要在畫面上看得到：講「發生什麼、怎麼辦」，用使用者的話寫。
2. 原始錯誤（代碼、狀態碼、回應內容）一律寫進 `ui.log`，不能只換成白話就把原文丟掉（#1753 的教訓）。
3. 讀不到資料時，要在原位說明「讀不到」，不准整塊消失（#1764 的教訓）。
4. 吞錯誤（`let _ =`、空的 catch、`unwrap_or_default` 蓋掉失敗）要寫註解說明理由，審查時逐一檢查。
5. 會重試的地方一定要有退避，也要有上限，不准後台一不通就每秒狂打（#1767 一審的教訓）。
6. 讀畫面判斷狀態（登入過期、選單、權限框）時，比對「行首」（去掉 ⎿ 這類前綴之後的開頭），不用「整行包含」。● 開頭的 AI 回覆、使用者打的字、轉進來的信，都不算（#1795、#1799 的教訓）。

## 四、畫面上的字

1. 不放開發者細節：檔案路徑、內部代號、HTTP 狀態碼、函式名稱都不能出現。這些寫進 log。
2. 按鈕寫「按下去會發生什麼」，不寫括號裡的自白，例如不寫「先關掉（照常進行）」。
3. 選項在某個外觀或平台下沒有作用，就要變灰，旁邊加一行說明，不准「看得到、選得了、卻沒作用」（#1790 的教訓）。外觀選項依所選外觀用不到時，改為隱藏、不是變灰（#1547 擁有者定）；隱藏只是不顯示，存檔的值不動。
4. 提醒或對話框一定要給使用者能做的事，例如「到那個視窗」「重試」。只有「知道了」的框，代表根本不需要跳出來（#1799、#1800 的教訓）。
5. 不需要使用者決定的進度（送出中、關閉中），在原位顯示、做完自己消失，不要用會擋住畫面的框。
6. 按鈕文字用動作說法，不用疑問句：寫「進行安裝」「進行更新」，不寫「怎麼安裝」「怎麼更新」（擁有者 11-22，#1548）。
7. 手機版、窄版的按鈕一律靠右排（擁有者 11-22，#1548）。
8. 上面兩條的適用範圍：之後新改的畫面照做；既有頁面不專程回頭改，下次動到那頁時順手改。

## 四之一、通知與系統訊息（2026-11-27）

由來：11-27 盤點，通知的種類表有三份而且對不上（設計文件 8 種、後台實際寄 18 種、前端分類表 15 種），訊息文字散在後台、兩支橋、前端、手機、發版工具六個地方，「收發室」開頭的前綴有六種寫法。原因是每張功能單都順手在自己那一段寫一句，沒有任何一處管整件事。

1. 新增一種系統通知，同一張 PR 先在 [通知種類](通知種類.md) 登記：種類代碼、分類、誰寄出、什麼時候寄。沒登記，守門測試會紅。
2. 前端的分類表要和登記表一致；要改某一種通知歸哪一類，改登記表和前端，兩邊同一張 PR。
3. 寄給夥伴視窗或群組的收發室訊息，前綴的用字由擁有者定；定案前暫以登記表為準。守門只擋舊寫法變多，不要求把既有的改掉：`[收發室]` 同時是辨認舊信的標記，要改之前先查清楚辨認規則會不會受影響。
4. 同一件事只寄一則、只有一種講法。要寄通知之前，先搜登記表和既有文字，已經有同一件事的通知就沿用，不另寫一句同義的話。
5. 通知的文字要照第四節：講「發生什麼、怎麼辦」，帶設備名時用設備頁上的名字，不用主機名稱。

## 五、設計先行

1. 新畫面、整頁改版、會改變擁有者操作習慣的，先出設計稿（三套外觀、寬窄，需要時加亮暗），asn真 審過，再給擁有者點頭，才寫程式。
2. 修毛病、內容不變的（換元件、排版小修），asn真 審過就定案，不拿去問擁有者。
3. **第 1 條那一類的畫面改動，先給擁有者確認，再一審（擁有者 2026-11-27 定）；第 2 條的小修照舊，不用問擁有者。** 確認的方式二選一：出設計稿，或直接做在網頁版上給擁有者看；網頁版上線前先用設計稿。確認過的畫面改動一審就能合，沒確認過的不准合；確認之後才延伸到電腦與手機。由來：擁有者說「畫面越快作出來越能調」，問題不在幾審，而在各夥伴各自亂做、通知和訊息沒有階級與範圍、四處亂放，沒有先對過就做出來了。
4. 新增任何通知、提示或訊息，設計稿或 PR 說明都要寫清楚三件事：**階級**（要使用者動手、知道就好、只留記錄）、**範圍**（給誰看、在哪些設備上出現）、**位置**（放在畫面規範允許的哪一個位置）。寫不出來的不做（擁有者 2026-11-27）。

## 六、PR 與審查

1. 每張 PR 照 PR 範本，填三個必填項：手機和電腦有沒有一起改、測試是不是真資料、回歸測試的名稱。沒填的，CI 會擋下來。
2. 審查人選與一審、二審的分工看「六之二、身分與審查」。審的時候要兼顧電腦端和手機端，除了看「改了什麼」，也要問「還有哪裡應該一起改卻沒改」。
3. 只改到一邊畫面的 PR，除非是平台本來就沒有的功能，一審直接退回。PR 範本檢查會自己看改了哪些檔：只動到手機或電腦其中一邊的頁面或樣式檔，說明裡就要有一行「只改一邊：原因」，沒寫會紅；審查的人要看這一句寫的原因成不成立。
4. 測試不准寫死「我是最新的 migration」這類會被下一張撞壞的斷言，只檢查相對順序（#1781、#1795 的教訓）。
5. 新加的相依套件，版本發布要超過 14 天；相依套件的相依也一樣要查。
6. 簽核一定要寫明 SHA。head 換了就要重簽；疊在別張上面的 PR，等下面那張合進 main 之後，要把 base 改回 main 再跑一次 CI。
7. 推上 main 的，必須是 CI 實際跑過的那個合併提交。臨時 CI 載具 PR（標題 `tmp:` 開頭，PR 範本檢查會豁免）只拿來跑 CI，用完一律關掉，絕不合併。
8. CI 失敗先看是哪一步失敗：下載逾時這類基礎設施問題可以重跑；測試失敗一定要查根因，不准靠重跑矇混過去。
9. 改了畫面上的文字，冒煙腳本和測試裡引用到的同一句話要一起搜出來一起改。
10. 新增或搬移設定，PR 要同時更新 [docs/設定值清單.md](設定值清單.md)（分類、預設值、存在哪裡、三平台、誰會讀它）；守門測試 `relay/asn/test/settings-list.test.mjs` 會擋沒登記的（含存檔欄位：新增、改名存檔欄位或 `localStorage` 鍵，要在清單登記 `file.<檔>.<鍵>`；鍵名以 Rust 設定層為準，前端常數在 `ui/lib/storage-keys.mjs`）。新設定要標 needs（`ui/lib/setting-needs.mjs`，沒有特殊需求也要寫 `[]`），平台欄照 needs 與能力表（`ui/shells/caps-*.mjs`）填：做不到寫「無（平台）：原因」，做得到只是沒做寫「無（未做）：原因」，守門測試會雙向比對。領隊排設定要放哪一類之前，先看這份清單。
11. 每張 PR 和每份審查報告都寫完整的 commit SHA（40 碼）；合併後在 PR 留言寫合併後的 SHA。
12. 沒在真機上看過的畫面，PR 裡要寫「沒在真機看過」，並列出還沒驗證的項目。
13. 終端送字、代答這類 PR（`term_send`、`term_answer`、`term_remote_*`）：審查報告要單獨寫一段「逐條走過每一種結束方式」，共六種：電腦確認、手機確認、手機拒絕、過期、取消、換分頁。每一種都寫出之後畫面和後端會變成什麼樣，寫完才給結論（#329、#330、#334 三次都是審查通過後才發現漏洞）。
14. 一張 PR 的審查結果合成一則發，不要連發好幾則。

## 六之一、大象與金魚

「大象」是記得所有討論脈絡的人，「金魚」是什麼都不記得、只看眼前文件的審查者。脈絡知道得越多，越容易把沒寫下來的事當成理所當然；金魚看不到這些，所以抓得出缺口。做法參考 Google 的 Elephant-Goldfish 設計審查。

1. 要寫程式的單，開工前由大象（開單或接單的人）把規格寫進 issue 本文，再派一個全新的子代理當金魚審規格。金魚只拿 issue 本文和程式碼，不給討論脈絡，也不給我們自己的看法。它挑出的缺口補進規格之後，才開工。
2. 審 PR 時派的子代理也一樣：只給單和程式，不給審查者自己的結論。
3. 版本規劃大改時，也要先讓金魚看過一次。

審查次數：

1. 一審就可以合：畫面、文字、前端邏輯、測試、文件、CI。
2. 維持兩審：動到正式後台（資料庫 migration、relay／Edge 函式），以及動到金鑰、簽章、發版權限的。
3. 由來：11-22 #2102 的後台函式在一審核可後，二審才抓到「寄通知丟例外會讓帳號回報整份回滾、每輪重複失敗」。
4. 畫面改動（擁有者 2026-11-27 定）：新畫面與會改變操作習慣的，照第五節第 3 條先給擁有者確認，確認過的一審就能合。版本規劃原有的「進 App 的項目維持兩審」（11-21）不再套用在畫面改動上；其餘照本節第 1、2 條。

交出 PR 之後：

1. CI 綠、交出審查後，開發的人直接照順序領下一張，不等審查和合併。
2. 審查打回要修時，先修 PR，再回頭做手上的新單。
3. 下一張若會改到同一批檔、或依賴還沒合的那張，先做順序裡不衝突的別張，等前一張合了再接（避免 #2092 那種 rebase 衝突）。

誰決定什麼（原本寫在 TEAM-FLOW）：

1. 夥伴互審過就可以自己合併、發版，不用等擁有者點頭（擁有者 10-26、10-27）；改到安全預設或別的程式設定檔的，要在群組寫清楚改了什麼。
2. 擁有者只決定產品方向；方向不明時先問，再動手。
3. 不直接推送到 main；合併由上表負責合併的人做。
4. 做了就收不回來、而且不在程式裡的事（倉庫公開、花錢、刪除線上資料），由擁有者決定。

審查用的帳號：寫的人、審的人、合併的人目前共用同一個 GitHub 帳號，GitHub 沒辦法強制「一定要別人核可」。在擁有者另外準備審查專用帳號之前，這一條靠人：審查留言要寫明審查者是誰、簽的是哪個 SHA；合併的人要核對留言裡的 SHA 等於 PR 現在的 head。

## 六之三、領單與拆項（擁有者 11-20；原本寫在 TEAM-FLOW）

1. 每個項目都要拆到可以被獨立驗證，不要包成一大包。每張單開工前，領隊先拆成小項；每項有自己的驗收方式（測試或實跑），能單獨合併、單獨驗。拆不出驗證方式的單，領隊不放行開工。
2. 每個小項動手的時間不超過 30 分鐘（等 CI、建置的機器時間不算）；做到 30 分鐘還沒交，就停下來回報領隊重拆，不硬做。查不明的問題改成每 30 分鐘交一次調查結果（查到哪、下一步），由領隊決定繼續、換人或重拆。拆得越細 PR 越多，這條要搭配 #1943（只動畫面的 PR 不跑全量建置）一起落實，避免動手 20 分鐘卻等建置 1 小時。
3. 不同平台或元件（電腦版、手機、Linux、官網、後台）一律各自一項，不綁在一起。例：自動發版拆成三條獨立管線：`asn-release.yml`（`v*` 標籤，電腦版）、`asn-release-android.yml`（`android-v*`）、`asn-release-linux.yml`（`linux-v*`）。一項卡住不擋其他項，其他項照合照發。
   - 和第一節「三邊最後要一致」怎麼並存（2026-11-27，依擁有者同日對畫面改動的決定整理）：建置、發版、部署各平台各自一項。畫面改動照第五節第 3 條，先確認、再延伸；延伸可以各平台各自一張，但都掛在同一張母單底下，全部做完才算完成。
4. 部署、試跑、切換、觀察這類工作做不到 30 分鐘一項：要指定一個負責人、開單、排進開發順序，負責到做完為止（第二之一節）。
5. 領取：手上的事做完，先領掛「待一審」的 PR 來審，再領新單。領單前先看單上有沒有已開的 PR 或「待發版」標籤，有就跳過。開工前先加「領取-名字」標籤，並在單上留言「【領取】名字 開始」。
6. 盤點、調查這類工作指名給一個人做，不要好幾個人各做一份（10-27 的頭像盤點同時出了三份）。盤點的結果要寫成有守門的清單（第零節第 3 條），不要只留在單上的留言裡；留言裡的數字過幾天就對不上程式。

## 六之四、群組與回報（原本寫在 TEAM-FLOW）

1. 群組每小時最多 20 則。回報合成一則，只在被點名或真的需要時才回。
2. 群組裡只寫 issue 或 PR 的編號加一兩句結論，細節寫在 issue 或 PR 裡。

## 七、後台與資料

1. migration 一定要附回復檔，回復檔的函式要和套用前的定義逐字相同，用靜態測試守住。
2. 兩支 migration 不要同時套。套完立刻煙測：寄信給本人（含推播）、群組三台都看得到、寄給夥伴視窗、名單正常。任何一項不通就用回復檔退回，不要原地修。
3. 正式資料庫只用 select，查資料時不選個人資料欄位（email、IP、信件內文）。
4. 部署順序一律是 migration → Edge → 用戶端；每一步都要讓還沒更新的舊版照常能用。
5. 新的對外入口（新動作、新網域、新登入方式）預設是關的，要明確設定才打開（例如網頁版沒設網域時整條路徑都關著，#1766）。

## 七之一、公開 repo

ASN 的 repo 是公開的。

1. 安全弱點、威脅分析、攻擊情境、受影響的清單，不准寫進 issue、PR、commit 訊息、程式註解或 docs。這些一律私信 asn真，或放在私人文件裡。
2. 擁有者的截圖不放進 issue 或 PR，用信寄給審查的人；需要的話，在 issue 裡用文字描述畫面。
3. 擁有者的個人資料（名字、email、聯絡人、帳號 ID）不寫進公開的地方，要提到就寫「擁有者」。

## 八、發版

1. 發版前在 30家用跑完整的 246 個截圖情境，報告附在 release PR 上。
2. Android 正式包要實機裝起來、實際打開，看 logcat 確認沒有閃退。
3. 手機只推內部測試軌，正式版要問擁有者。
4. CHANGELOG 用使用者的話寫，不寫檔名和內部代號。
5. 已發的版本內容以 `relay/asn/CHANGELOG.md` 與 GitHub Release 為準，不另外手寫一張「已發」表（手寫的那張 11-22 之後就沒人更新，落後了 40 版）。
6. 官網的藍圖、待辦、版本與會議記錄都在資料庫，寫法見 `site/README.md`；發版後同一天更新，不另開 PR 改頁面。
7. 發版順序：電腦版、Android 官網版、Play、官網部署（原本寫在 TEAM-FLOW）。

## 九、追蹤

1. 每份例行報告都寫「本期復發幾件」。數字用 `node .github/scripts/recur-report.mjs --since <日期>` 算，不靠人數（11-27 盤點：整個 repo 貼過「復發」標籤的只有 2 張，等於沒在量）。
2. 擁有者提出的規則，先寫進這份，再照著做。不要只記在某個視窗的腦子裡，因為視窗會重開。

## 九之一、開發順序與版號（擁有者 11-19～11-21 定；原本寫在版本規劃）

1. 開發順序依重要性與依賴排，地基在前；不照版號，也不照單號先後。擁有者 2026-11-27 澄清：當初說的是「自己領、別照版號」，沒有要大家照單號排；問題是一直沒有人依重要性與依賴把地基往前排。
2. 分三層，上一層沒有人領的才領下一層：一、正在壞的（當機、資料遺失、正在發生的事故）；二、地基；三、功能。同一層裡先看依賴，再看重要性，最後才看單號。挪動記在 [版本規劃](版本規劃.md) 的「調整紀錄」。
3. 地基（擁有者 2026-11-27 定「地基先行」）：做完之後每張單都少寫一份、或少錯一次的工作，例如把兩份收成一份、舊實作退場、補唯一出口、把靠人的規則改成機器擋、訊息與通知的規範。哪些單算地基、彼此的先後，由負責規劃的提出、擁有者確認後貼「地基」標籤；清單放在 GitHub 上標題為「地基清單」的那張單，不在文件裡手寫。
4. 依賴：單上寫「依賴 #A」，A 還沒合進 main 之前 B 不能領。一件事要分幾步才成立的算同一張，拆成幾個 PR，最後一個合了才算完成。
5. 版號在發版時才給，照發的先後連號遞增，由 asn真 統一改。哪張先完成、合進 main，就跟著下一個版號發；某一張卡住，只是它自己晚發，不擋別人。PR 不掛里程碑。
6. 只有不會進 App 的不佔版本：測試、CI、文件、調查不佔版本。改到 App 程式碼的，就算是內部重構也算一個發版項目。
7. 一張單定好範圍就不再加料；新想法另開單，排在最後。「這張單會不會多寫出一份副本」不算加料，是開工前一定要問的事（第二之一節）。
8. 穩定性排在介面前面；同性質的放在相鄰。
9. 需要擁有者驗的項目不擋發版，累積成清單一次給他。
