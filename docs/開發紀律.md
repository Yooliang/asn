# ASN 開發紀律

> 這份是 ASN 所有開發夥伴（人與 AI）都要照做的規則。寫 PR、審 PR、發版前，照這份逐條對。
> 由來：2026-11-19 一天之內，擁有者撞到好幾個「修過又復發」「手機和電腦不一樣」「壞了卻沒有提示」的問題。擁有者的原話：「不是我說一條改一條吧，自己制定規則與紀律」。
> 規則有改，直接改這份，PR 標題寫「紀律：」開頭。

## 一、一份畫面，三個平台

1. 手機、電腦、網頁共用同一份功能、同一份介面元件和同一份樣式。三邊只有「版面」可以不同（電腦雙欄、手機先清單再內容、網頁同電腦），另外就是平台本來就沒有的功能（系統匣、推播、Play 更新、右鍵、長按）。
2. 不准做出某一邊獨有的樣子：新畫面或新樣式三邊一起做，要不然就都不做。
3. 使用者看得到的文字只放一份常數，三邊都從那裡引用，不准在 `m.html`／`list.html` 各寫一次。
3-1. 同一條規則（例如誰算在線、誰能改名、額度怎麼算）只能有一個函式實作，所有入口都呼叫它。11-06～11-19 的 19 組復發裡，有 7 組是「規則寫死在好幾處」，是最大宗。
4. 修毛病之前，先找有沒有其他「兄弟副本」：用症狀關鍵字搜手機和電腦兩邊，PR 說明寫出搜了什麼、找到哪幾處。只修其中一處，就等於留了一個復發。

## 二、修毛病：從根因修，留下守門測試

1. 先找到根因再動手。只修顯示、不修根因的，要在 PR 和給擁有者的回報裡講明「根因沒修」。
2. 每個修正都要附一支回歸測試，而且要證明「拿掉修正會紅燈」。PR 說明寫出測試名稱。
3. 測試用真資料或真路徑。例如畫面要吃的是後台存的那份資料，就拿資料庫裡實際存的那份當輸入，不准自己造一份剛好會過的假資料（#1126 的教訓）。
4. 只修壞掉的那條路。正常運作的功能不要順手加守門、不要順手改流程；看到的延伸問題另外開單。
5. 修過又復發的問題，加上「復發」標籤。修的時候一定要加一支以單號命名的守門測試（例如 `test('#1803 設備名稱只有一個來源', …)`）。

## 三、不准靜默失敗

1. 失敗一定要在畫面上看得到：講「發生什麼、怎麼辦」，用使用者的話寫。
2. 原始錯誤（代碼、狀態碼、回應內容）一律寫進 `ui.log`，不能只換成白話就把原文丟掉（#1753 的教訓）。
3. 讀不到資料時，要在原位說明「讀不到」，不准整塊消失（#1764 的教訓）。
4. 吞錯誤（`let _ =`、空的 catch、`unwrap_or_default` 蓋掉失敗）要寫註解說明理由，審查時逐一檢查。
5. 會重試的地方一定要有退避，也要有上限，不准後台一不通就每秒狂打（#1767 一審的教訓）。
6. 讀畫面判斷狀態（登入過期、選單、權限框）時，比對「行首」（去掉 ⎿ 這類前綴之後的開頭），不用「整行包含」。● 開頭的 AI 回覆、使用者打的字、轉進來的信，都不算（#1795、#1799 的教訓）。

## 四、畫面上的字

1. 不放開發者細節：檔案路徑、內部代號、HTTP 狀態碼、函式名稱都不能出現。這些寫進 log。
2. 按鈕寫「按下去會發生什麼」，不寫括號裡的自白，例如不寫「先關掉（照常進行）」。
3. 選項在某個外觀或平台下沒有作用，就要變灰，旁邊加一行說明，不准「看得到、選得了、卻沒作用」（#1790 的教訓）。
4. 提醒或對話框一定要給使用者能做的事，例如「到那個視窗」「重試」。只有「知道了」的框，代表根本不需要跳出來（#1799、#1800 的教訓）。
5. 不需要使用者決定的進度（送出中、關閉中），在原位顯示、做完自己消失，不要用會擋住畫面的框。

## 五、設計先行

1. 新畫面、整頁改版、會改變擁有者操作習慣的，先出設計稿（三套外觀、寬窄，需要時加亮暗），asn真 審過，再給擁有者點頭，才寫程式。
2. 修毛病、內容不變的（換元件、排版小修），asn真 審過就定案，不拿去問擁有者。

## 六、PR 與審查

1. 每張 PR 照 PR 範本，填三個必填項：手機和電腦有沒有一起改、測試是不是真資料、回歸測試的名稱。沒填的，CI 會擋下來。
2. 兩位審查者：一位熟電腦端、一位熟手機端。審的時候除了看「改了什麼」，也要問「還有哪裡應該一起改卻沒改」。
3. 只改到一邊畫面的 PR，除非是平台本來就沒有的功能，一審直接退回。
4. 測試不准寫死「我是最新的 migration」這類會被下一張撞壞的斷言，只檢查相對順序（#1781、#1795 的教訓）。
5. 新加的相依套件，版本發布要超過 14 天；相依套件的相依也一樣要查。
6. 簽核一定要寫明 SHA。head 換了就要重簽；疊在別張上面的 PR，等下面那張合進 main 之後，要把 base 改回 main 再跑一次 CI。
7. 推上 main 的，必須是 CI 實際跑過的那個合併提交。
8. CI 失敗先看是哪一步失敗：下載逾時這類基礎設施問題可以重跑；測試失敗一定要查根因，不准靠重跑矇混過去。
9. 改了畫面上的文字，冒煙腳本和測試裡引用到的同一句話要一起搜出來一起改。

## 七、後台與資料

1. migration 一定要附回復檔，回復檔的函式要和套用前的定義逐字相同，用靜態測試守住。
2. 兩支 migration 不要同時套。套完立刻煙測：寄信給本人（含推播）、群組三台都看得到、寄給夥伴視窗、名單正常。任何一項不通就用回復檔退回，不要原地修。
3. 正式資料庫只用 select，查資料時不選個人資料欄位（email、IP、信件內文）。
4. 部署順序一律是 migration → Edge → 用戶端；每一步都要讓還沒更新的舊版照常能用。
5. 新的對外入口（新動作、新網域、新登入方式）預設是關的，要明確設定才打開（例如網頁版沒設網域時整條路徑都關著，#1766）。

## 七之一、公開 repo

ASN 的 repo 是公開的。

1. 安全弱點、威脅分析、攻擊情境、受影響的清單，不准寫進 issue、PR、commit 訊息、程式註解或 docs。這些一律私信 asn真，或放在私人文件裡。
2. 擁有者的截圖不放進 issue 或 PR，用信寄給審查的人；需要的話，在 issue 裡用文字描述畫面。
3. 擁有者的個人資料（名字、email、聯絡人、帳號 ID）不寫進公開的地方，要提到就寫「擁有者」。

## 八、發版

1. 發版前在 30家用跑完整的 246 個截圖情境，報告附在 release PR 上。
2. Android 正式包要實機裝起來、實際打開，看 logcat 確認沒有閃退。
3. 手機只推內部測試軌，正式版要問擁有者。
4. CHANGELOG 用使用者的話寫，不寫檔名和內部代號。

## 九、追蹤

1. 每份例行報告都寫「本期復發幾件」。
2. 擁有者提出的規則，先寫進這份，再照著做。不要只記在某個視窗的腦子裡，因為視窗會重開。
